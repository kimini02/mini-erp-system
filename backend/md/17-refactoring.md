# 리팩토링 — 동작은 그대로, 읽기 쉽게 (배포 전)

> 기준: [00-coding-convention.md](00-coding-convention.md) v2.0(이 단계에서 현재 구조에 맞게 고침), [11-architecture.md](11-architecture.md).
> 목표: 코드를 처음 보는 사람이 읽을 수 있게 만든다. **동작·API 응답·DB·실행되는 SQL은 한 글자도 바꾸지 않는다.**
> 순서: M5 두 브랜치를 develop에 병합 → 이 리팩토링 → 배포·기준값 측정(16) → 회사 규모 데이터로 문제 찾기(18).
> 이유: 18의 전후 비교와 블로그 링크에 리팩토링 변경이 섞이지 않게, 기준값을 한 번만 재도록.

---

## 0. 결정

| 결정 | 이유 · 버린 것 |
|---|---|
| **바꾸지 않는 것: 동작, API 응답 JSON, 오류 코드·메시지, DB·마이그레이션, 실행되는 SQL** | 리팩토링과 성능 개선을 섞지 않음. 18에서 "무엇이 빨라졌나"가 리팩토링 영향을 받지 않음 |
| **직접 SQL(`SqlStore`) 유지** | JPA 전환은 버림. 범위 조건(AD-03)·여러 테이블 조인·홈 쿼리 수 고정 규칙을 SQL로 직접 다루고 있고, 18의 EXPLAIN 분석과 바로 이어짐. 전환하면 SQL이 바뀌어 위 원칙도 깨짐 |
| **응답은 타입이 있는 record로** (`ApiResponse<?>` + `Map<String,Object>` → `ApiResponse<구체 타입>`) | 지금 API 93개가 타입 없는 Map. 키 오타를 컴파일러가 못 잡고, Swagger에 응답 모양이 안 나오고, 코드만 봐서는 응답 모양을 알 수 없음 |
| **SQL은 `repository/` 패키지의 쿼리 클래스로 옮김, 문자열은 그대로** | 지금 26개 서비스 파일 안에 SQL과 업무 규칙이 섞여 있음. 18에서 고칠 쿼리가 이름 있는 메서드가 되어 글·커밋에서 가리키기 쉬움 |
| **안전망을 먼저 만들고 시작** (SQL 지문 + 응답 스냅샷) | "테스트가 통과했다"만으로는 응답 숫자 표현(10 → 10.0)이나 null 키 누락 같은 변화를 놓칠 수 있음. 전후 기록을 기계적으로 비교 |
| 새 계층·인터페이스·패턴·라이브러리 추가 안 함 | 읽기 쉽게가 목적. 추상화를 늘리면 오히려 읽기 어려워짐. 포맷터 플러그인도 pom에 추가하지 않음 |
| 요청 본문은 지금 record 그대로 | 이미 타입이 있음. 검증 규칙을 바꾸면 오류 응답이 바뀜 |

## 1. 안전망 (가장 먼저, 리팩토링 전 코드에서 기준선 생성)

테스트 전용 코드만 추가합니다. 운영 코드는 건드리지 않습니다.

### 1.1 SQL 지문
- 기존 `JdbcProbe`를 넓혀 **전체 테스트 실행 중 실행된 SQL**을 기록합니다. 정규화 방식은 지금처럼 공백 압축 + 소문자입니다.
- 기록할 것:
  - 테스트별 실행 SQL 목록과 순서
  - 테스트별 쿼리 수
  - 전체의 서로 다른 SQL 집합
- 파라미터 값은 기록하지 않습니다(테스트마다 무작위 아이디가 있음).
- 비교 기준: 서로 다른 SQL 집합과 테스트별 쿼리 수가 **완전히 같아야** 합니다. 실행 순서가 바뀌면 이유를 보고합니다.

### 1.2 응답 스냅샷
- MockMvc를 쓰는 모든 테스트의 요청·응답을 기록합니다. 테스트 전용 설정으로 `MockMvcBuilderCustomizer` 같은 훅을 씁니다.
  - 요청: 메서드, 경로, 상태 코드
  - 응답: 본문 JSON
- 실행마다 달라지는 값만 가립니다(예: `test-<UUID>` 아이디, 자동 증가 id). **가린 필드 목록을 보고서에 남깁니다.** `timestamp`는 고정 시계라 가리지 않습니다.
- 비교 기준: 다음이 글자 단위로 같아야 합니다.
  - 키 이름, 중첩 구조, null 키의 유무
  - 숫자 표현(`10`과 `10.0`, `10.0`과 `10.00`은 다름)
  - 날짜 형식, 배열 순서
- 객체 안의 키 순서는 비교에서 무시하되, 가능하면 기존 순서를 유지합니다.
- 오류 응답(4xx·5xx)도 같은 기준으로 비교합니다.

### 1.3 기준선
- develop(M5 병합 후)에서 전체 UTC 테스트를 돌려 두 기록을 만들고, 기준선으로 커밋합니다. 위치는 `backend/src/test/resources/refactoring-baseline/`입니다.
- 비교 도구는 차이를 "어느 테스트의 어느 요청, 어느 키"로 보여 줘야 합니다.
- 기준선 자체가 안정적인지 확인합니다. **리팩토링 전 코드로 두 번 돌려 차이가 0**이어야 합니다. 0이 아니면 가릴 필드를 먼저 정리합니다.

## 2. 단계

각 단계는 도메인별로 작게 커밋합니다. **커밋마다 전체 UTC 테스트 통과 + SQL 지문 동일 + 응답 스냅샷 동일**이어야 합니다.

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | 안전망과 기준선(1장) | 테스트 코드만 |
| 2 | 형식 정리 | 기계적 변경만. 이름·구조는 그대로 |
| 3 | SQL 위치 이동 | 문자열 그대로 옮기기만 |
| 4 | 응답 record + 이름 + 메서드 나누기 | 도메인 묶음 세 번으로 나눠 진행. 한 파일을 한 번만 크게 고치도록 셋을 같이 함 |

### 2.1 형식 정리 (2단계)
- **한 줄에 한 문장.** 필드 선언, `var` 여러 개, `if(...) throw ...; return ...;` 한 줄 몰아쓰기를 모두 풉니다.
- 한 줄은 **120자 이내**입니다. SQL 텍스트 블록 안은 예외입니다(SQL을 바꾸지 않음).
- 들여쓰기 4칸, 연산자·쉼표 뒤 공백, 어노테이션은 한 줄에 하나씩.
- 와일드카드 import는 그대로 둡니다. 변경량만 늘고 읽기 이득이 작습니다.
- 테스트 코드도 형식 정리만 합니다.

### 2.2 SQL 위치 이동 (3단계)
- SQL 문자열은 `domain/{도메인}/repository/` 패키지의 클래스에만 둡니다. 예외는 `global/persistence/SqlStore`와 `global/` 공통 쿼리입니다.
  - 서비스·handler·batch 안의 SQL을 옮깁니다.
  - `service/` 패키지에 있는 기존 `*Store`·`*Query`·`*Queries` 클래스는 이름을 그대로 두고 `repository/`로 옮깁니다.
- 새로 만드는 클래스 이름: 읽기 위주는 `{도메인}Queries`, 쓰기 위주는 `{도메인}Store`. 메서드 이름은 하는 일을 말합니다(예: `countMonthlyAbsences`).
- **SQL 문자열·파라미터 이름·동적 조각(예: `FOR UPDATE` 붙이기)은 한 글자도 바꾸지 않습니다.** SQL 지문으로 확인합니다.
- **옮기는 것은 SQL 실행과 결과 받기까지만입니다.** 검증하고 `BusinessException`·`IllegalArgumentException`을 던지는 코드는 서비스에 남깁니다.
  - 주의: `@Repository` 빈은 JPA의 예외 변환을 받습니다. 그래서 그 안에서 던진 `IllegalArgumentException`이나 `IllegalStateException`이 `InvalidDataAccessApiUsageException`으로 바뀔 수 있고, 오류 응답도 달라집니다.
  - 오류 응답 스냅샷으로 확인합니다.
- 트랜잭션 경계는 그대로입니다. 쿼리 클래스에 `@Transactional`을 새로 붙이지 않습니다.

### 2.3 응답 record · 이름 · 메서드 (4단계)
**응답 record**
- 위치는 `domain/{도메인}/dto/`, 이름은 `{도메인}{동작}ResponseDto`입니다(규칙 문서 4장). 안쪽 구조는 중첩 record로 만듭니다.
- 변환은 **SQL 결과를 지금처럼 `SqlStore`의 행으로 받고, record의 정적 메서드 `from(행)`에서 한 번만** 합니다.
  - 행을 record로 바로 받는 `DataClassRowMapper` 방식은 버립니다. `SqlStore`의 날짜 변환을 거치지 않아 JSON의 날짜 모양이 바뀔 수 있기 때문입니다.
- 필드 타입은 **지금 JSON과 똑같이 나오는 타입**을 고릅니다.
  - DECIMAL은 `BigDecimal`(소수 자릿수 유지), BIGINT는 `long`/`Long`, null이 올 수 있으면 박싱 타입을 씁니다.
  - 지금 `null`로 나가는 키는 record에서도 `null`로 나가야 합니다. 키를 빼면 안 됩니다.
- 컨트롤러 반환 타입은 `ApiResponse<구체 타입>`입니다. 201 같은 상태 코드는 지금처럼 `@ResponseStatus`로 둡니다.
- `SqlStore.map(...)`은 응답을 만드는 데 쓰지 않습니다. SQL 파라미터를 넘길 때만 씁니다.

**이름**
- 한두 글자 변수(`r`, `l`, `x`, `u`, `d`)를 뜻이 드러나는 이름으로 바꿉니다. 루프 인덱스 `i`는 그대로 둡니다. SQL 안의 별칭은 바꾸지 않습니다.
- 컨트롤러·서비스 메서드는 규칙 문서 10.2를 따릅니다(예: `in()` → `clockIn()`). URL은 그대로입니다.

**메서드 나누기**
- 한 메서드가 한 가지 일을 하도록, 의미 단위로 이름 붙은 private 메서드로 나눕니다. 줄 수 기준보다 "이름으로 설명되는가"를 봅니다.
- 주석은 "왜"를 설명하는 것만 남깁니다. 기존의 "왜" 주석은 지우지 않습니다.

**도메인 묶음** (묶음마다 리뷰를 받은 뒤 다음으로 넘어감)
1. org · user · permission
2. approval · leave · overtime
3. attendance · calendar · home · notification · project · task · dashboard

## 3. 바꾸지 않는 것 (확인 목록)

- `frontend/`, `backend/md/`(이 문서와 규칙 문서는 Claude가 관리), `V1~V6` 마이그레이션, `.claude/`
- API 경로, 요청 본문, 응답 JSON, 상태 코드, 오류 코드·메시지
- 실행되는 SQL(문자열·파라미터·순서), 인덱스, 스키마, 트랜잭션 경계, 격리 수준
- 홈 쿼리 수 고정 등 기존 측정 테스트의 기대값
- 운영 설정(`application-prod.properties`), 배포 스크립트

리팩토링 중 버그를 발견해도 **고치지 않고 기록만** 합니다. 고치면 응답이 바뀌어 안전망이 의미를 잃습니다. 따로 보고하면 단계가 끝난 뒤 별도 `fix` 커밋으로 처리합니다.

## 4. 프론트엔드 (Claude)

- 400줄이 넘는 페이지(결재 작성·홈·부서·사원·역할 등)를 화면 단위 컴포넌트로 나눕니다. 반복되는 표·모달·빈 상태는 공용 컴포넌트로 모읍니다.
- 화면 모양과 동작은 그대로입니다. 목 데이터 모드에서 주요 화면을 리팩토링 전후로 캡처해 비교합니다.
- 목 데이터 파일(`api/mock/`)은 개발용으로 유지하되, 응답 모양이 백엔드 record와 같은지 함께 확인합니다.
- 형식은 Prettier 3.3.3(개발 의존성, 사용자 승인 2026-10-28)으로 맞춥니다. 백엔드는 포맷터 플러그인을 넣지 않는다는 0장 결정과 다르며, 프론트 생태계의 표준 도구이고 배포물에 들어가지 않기 때문입니다.
- 진행 기록과 안전망(화면 20개·모달 13개 비교) 결과는 [docs/refactoring/F-01](../../docs/refactoring/F-01-frontend-readability.md)에 있습니다. 안전망에서 찾은 기존 버그는 KI-08(캘린더 구 API), KI-09(목 모드 내 프로필)입니다.
