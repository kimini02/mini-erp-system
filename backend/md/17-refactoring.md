# 리팩토링 — 동작은 그대로, 읽기 쉽게 (배포 전)

> 기준: [00-coding-convention.md](00-coding-convention.md) v2.0(이 단계에서 현재 구조에 맞게 고침), [11-architecture.md](11-architecture.md).
> 목표: 코드를 처음 보는 사람이 읽을 수 있게 만든다. **동작·API 응답·DB·실행되는 SQL은 한 글자도 바꾸지 않는다.**
> 순서: M5 두 브랜치를 develop에 병합 → 이 리팩토링 → 배포·기준값 측정(16) → 회사 규모 데이터로 문제 찾기(18).
> 이유: 18의 전후 비교와 블로그 링크에 리팩토링 변경이 섞이지 않게, 기준값을 한 번만 재도록.
> 개정(2026-11-01): 1.1·1.2·1.3·1.4·2장·5장 — 기준선 안정성과 SQL 비교 기준 강화(R-01 리뷰 결과).
> 개정(2026-11-01, 2차): 2.1·5장 — 형식 정리의 바이트코드 동일 검사, 문자열 리터럴 예외, 외부 포매터 금지.
> 개정(2026-11-06, 3차): 2.1·5장 — 줄 바꿈 위치, 매개변수·타입 어노테이션, 텍스트 블록 닫는 줄, 소스 보존 검사(R-02 리뷰 결과).

## 0. 결정

| 결정 | 이유 · 버린 것 |
|---|---|
| **바꾸지 않는 것: 동작, API 응답 JSON, 오류 코드·메시지, DB·마이그레이션, 실행되는 SQL** | 리팩토링과 성능 개선을 섞지 않음. 18에서 "무엇이 빨라졌나"가 리팩토링 영향을 받지 않음 |
| **직접 SQL(`SqlStore`) 유지** | JPA 전환은 버림. 범위 조건(AD-03)·여러 테이블 조인·홈 쿼리 수 고정 규칙을 SQL로 직접 다루고 있고, 18의 EXPLAIN 분석과 바로 이어짐. 전환하면 SQL이 바뀌어 위 원칙도 깨짐 |
| **응답은 타입이 있는 record로** (`ApiResponse<?>` + `Map<String,Object>` → `ApiResponse<구체 타입>`) | 지금 API 93개가 타입 없는 Map. 키 오타를 컴파일러가 못 잡고, Swagger에 응답 모양이 안 나오고, 코드만 봐서는 응답 모양을 알 수 없음 |
| **SQL은 `repository/` 패키지의 쿼리 클래스로 옮김, 문자열은 그대로** | 지금 26개 서비스 파일 안에 SQL과 업무 규칙이 섞여 있음. 18에서 고칠 쿼리가 이름 있는 메서드가 되어 글·커밋에서 가리키기 쉬움 |
| **안전망을 먼저 만들고 시작** (SQL 지문 + 응답 스냅샷) | "테스트가 통과했다"만으로는 응답 숫자 표현(10 → 10.0)이나 null 키 누락 같은 변화를 놓칠 수 있음. 전후 기록을 기계적으로 비교 |
| 새 계층·인터페이스·패턴·라이브러리 추가 안 함 | 읽기 쉽게가 목적. 추상화를 늘리면 오히려 읽기 어려워짐. 포맷터 플러그인도 pom에 추가하지 않음 |
| 요청 본문은 지금 record 그대로 | 이미 타입이 있음. 검증 규칙을 바꾸면 오류 응답이 바뀜 |

## 1. 안전망 (가장 먼저, 리팩토링 전 코드에서 기준선 생성)

테스트 전용 코드만 추가합니다. 운영 코드는 건드리지 않습니다.

### 1.1 SQL 지문
- 기존 `JdbcProbe`를 넓혀 **전체 테스트 실행 중 실행된 SQL**을 기록합니다. 정규화 방식은 지금처럼 공백 압축 + 소문자입니다.
- 기록할 것(테스트, `@BeforeAll` 같은 실행 단위마다):
  - 실행 SQL 목록과 순서(같은 SQL이 연달아 나오면 횟수로 묶음)
  - 쿼리 수
  - 테스트 스레드가 아닌 스레드에서 SQL이 실행됐는지(`workerSql`)
  - 전체의 서로 다른 SQL 집합
- 파라미터 값은 기록하지 않습니다(테스트마다 무작위 아이디가 있음).
- 비교 기준: 아래가 하나라도 다르면 **실패**입니다.
  - 전체의 서로 다른 SQL 집합
  - 테스트별 쿼리 수와 **SQL별 실행 횟수**. 전체 쿼리 수가 같아도 한 SQL의 실행 1회가 다른 SQL로 옮겨 가면 실패입니다.
  - `workerSql` 표시. SQL이 다른 스레드로 옮겨 가는 것도 동작 변화입니다.
  - 테스트 스레드에서만 SQL이 실행되는 테스트(직렬 테스트)의 실행 순서
- 여러 스레드가 겹쳐 실행되는 테스트는 실행마다 순서가 달라질 수 있습니다. 그래서 순서 변경은 **경고로 보고**하고 이유를 적습니다. 경고 대상인지는 기준선의 `workerSql`로 판단합니다.
  - 다른 스레드에서 돌아도 요청을 한 번에 하나씩 보내는 테스트는 예외입니다(예: 실제 HTTP를 순서대로 보내는 M5 운영 설정 테스트). 이름과 이유를 적은 **순서 엄격 목록**에 넣어 실패로 다룹니다.
- 그 밖의 예외는 테스트 이름, 이유, **바뀌어도 되는 SQL**을 적은 허용 목록으로만 둡니다. 범위는 테스트 전체가 아니라 그 SQL로 한정합니다.
  - 지금 예외는 M5 `@BeforeAll` 하나입니다. 테스트 코드의 `Map.of` 순회 때문에 `CREATE USER` 두 줄이 서로 바뀝니다.
- 비교 횟수에서 빼는 SQL은 잠금 대기를 확인하는 진단 조회(`information_schema.innodb_lock_waits` 폴링문) 하나뿐입니다. 원본 기록에는 남깁니다.

### 1.2 응답 스냅샷
- MockMvc를 쓰는 모든 테스트의 요청·응답을 기록합니다. 테스트 전용 설정으로 `MockMvcBuilderCustomizer` 같은 훅을 씁니다.
  - 요청: 메서드, 경로, 상태 코드
  - 응답: 본문 JSON
- 실행마다 달라지는 값만 가립니다(예: `test-<UUID>` 아이디, 자동 증가 id). **가린 필드 목록을 보고서에 남깁니다.** `timestamp`는 고정 시계라 가리지 않습니다.
- 비교 기준: 다음이 글자 단위로 같아야 합니다.
  - 키 이름, 중첩 구조, null 키의 유무
  - 숫자 표현(`10`과 `10.0`, `10.0`과 `10.00`은 다름)
  - 날짜 형식, 배열 순서
- 객체 안의 키 순서는 비교에서 무시하되, 가능하면 기존 순서를 유지합니다.
- 오류 응답(4xx·5xx)도 같은 기준으로 비교합니다.
- 다른 스레드에서 보낸 동시 요청의 응답은 도착 순서가 실행마다 다릅니다. 그래서 같은 경로·상태 코드끼리 묶어 순서 없이 비교합니다. 응답 본문 안의 배열 순서는 그대로 비교합니다.

### 1.3 기준선
- develop(M5 병합 후)에서 기록을 켜고 전체 UTC 테스트를 돌려 기준선으로 커밋합니다. 위치는 `backend/src/test/resources/refactoring-baseline/`입니다.
- 비교 도구는 차이를 "어느 테스트의 어느 요청, 어느 키"로 보여 줘야 합니다.
- 같은 내용을 다시 기록하면 파일 바이트도 같아야 합니다(JSON 키 순서 고정). 그래야 git diff와 해시로 바뀐 곳을 볼 수 있습니다.
- 기준선 자체가 안정적인지 확인합니다.
  - 리팩토링 전 코드로 **기록 5회**를 돌립니다. 각각을 기준선과 비교해 차이가 0이어야 합니다.
  - **리뷰어가 별도 복사본에서 1회 더** 돌려 차이 0을 확인합니다.
  - 순서 경고가 나온 테스트의 합집합과 이유를 기록합니다.
  - 차이가 나면 가릴 필드부터 늘리지 않고 원인을 먼저 찾습니다. 경쟁 결과 때문이면 1.4로 처리 순서를 고정합니다. 실제 계약 변화를 가리면 안 됩니다.
- 왜 5회와 독립 1회인가: 처음 기준은 2회였습니다. 연차 조정과 휴가 상신이 동시에 들어가는 테스트에서 두 번 모두 우연히 같은 쪽이 이겨 차이 0이 나왔습니다. 리뷰어의 별도 실행에서는 반대쪽이 이겨 쿼리 수가 349에서 325로 줄고 차이가 21건 났습니다. 같은 환경에서 몇 번 돌리는 것만으로는 이런 경쟁을 놓칠 수 있습니다.

### 1.4 동시 요청 테스트의 기록 순서
- 동시 요청 테스트는 둘로 나눕니다.
  - **대칭 경쟁**: 같은 사용자·대상·입력의 요청끼리 겨룹니다(예: 같은 문서를 같은 결재자가 두 번 승인). 누가 이겨도 응답과 SQL의 묶음이 같으므로 그대로 둡니다.
  - **비대칭 경쟁**: 서로 다른 경로나 동작이 겨룹니다(예: 승인과 회수, 상신과 연차 조정). 이긴 쪽에 따라 SQL과 응답이 달라집니다.
- 비대칭 경쟁은 **기록할 때만** 정해진 순서(메서드·경로 순)로 하나씩 처리합니다.
  - 대상 테스트 목록과 정책 이름(`…-v2`처럼 버전 포함)을 기록에 남깁니다.
  - 목록이 바뀌면 버전을 올리고 기준선을 다시 만듭니다.
- 기록을 끈 기본 실행에는 이 순서 고정을 설치하지 않습니다. 실제 동시성 검증은 기본 실행이 맡습니다.
- latch 등으로 순서를 이미 강제하는 테스트는 다시 묶지 않습니다(교착 위험).
- 동시 요청 테스트를 새로 추가하면 대칭인지 비대칭인지 판단해 목록과 근거를 갱신합니다. URL이 같다는 것만으로 대칭이라고 판단하지 않습니다.

## 2. 단계

각 단계는 도메인별로 작게 커밋합니다.

- **커밋마다** 기록을 켠 전체 UTC 실행 1회가 모두 통과하고, 기준선과 비교해 차이가 0이어야 합니다(SQL 지문 + 응답 스냅샷).
- 기록 실행은 1.4 때문에 일부 경쟁을 순서대로 처리하므로 실제 동시성을 다 검증하지 못합니다. 그래서 **기록을 끈 전체 UTC 실행**도 통과해야 합니다.
  - 단계나 도메인 묶음이 끝날 때마다 1회
  - 잠금·트랜잭션과 관련된 코드(`FOR UPDATE` 쿼리, 동시 요청 테스트가 부르는 서비스)를 옮기거나 고친 커밋은 그 커밋에서도 1회

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | 안전망과 기준선(1장) | 테스트 코드만 |
| 2 | 형식 정리 | 기계적 변경만. 이름·구조는 그대로 |
| 3 | SQL 위치 이동 | 문자열 그대로 옮기기만 |
| 4 | 응답 record + 이름 + 메서드 나누기 | 도메인 묶음 세 번으로 나눠 진행. 한 파일을 한 번만 크게 고치도록 셋을 같이 함 |

### 2.1 형식 정리 (2단계)
- **한 줄에 한 문장.** 필드 선언, `var` 여러 개, `if(...) throw ...; return ...;` 한 줄 몰아쓰기를 모두 풉니다.
- 한 줄은 **120자 이내**(문자 수 기준)입니다. SQL 텍스트 블록 안은 예외입니다(SQL을 바꾸지 않음).
- 들여쓰기 4칸, 이어지는 줄 8칸, 연산자·쉼표 뒤 공백.
- **줄 바꿈**은 120자를 넘는 줄만 합니다. **넘치는 식의 가장 바깥 구조부터** 나눕니다.
  - 바깥에서 나눠 120자 안에 들어가면 안쪽은 나누지 않습니다.
  - 나눈 조각이 아직 넘치면 그 조각에 같은 규칙을 다시 적용하고, 그 조각이 시작된 줄보다 8칸 더 들여씁니다.
  - 가장 바깥 구조에 따라 나누는 곳이 다릅니다.
    1. **인자 목록**: 쉼표 뒤에서 나누고, 한 줄에 들어갈 만큼 채웁니다.
       - 키와 값을 번갈아 받는 호출(`SqlStore.map(...)`, `Map.of(...)`)은 키·값 쌍이 현재 줄에 다 안 들어가면 쌍째로 다음 줄로 보냅니다.
       - 키와 값 하나만으로 120자를 넘을 때만 값을 다음 줄로 보냅니다. 이때 다음 쌍은 새 줄에서 시작합니다.
       - 값이 삼항이라 쌍이 넘치면 키와 조건을 같은 줄에 두고, `?`·`:` 줄을 8칸 더 들여씁니다(`"actor", h.get("actor_id") == null` ⏎ `? null` ⏎ `: map(...)`).
       - **배열 초기화** `{ … }`(어노테이션 값 포함)도 인자 목록과 같습니다. 블록이 아니므로 `{` 뒤와 `}` 앞에서 줄을 바꾸지 않습니다(`new String[] { "id" }`, `@Target({ ElementType.METHOD, ElementType.TYPE })`).
    2. **호출이 2개 이상 이어진 체인**: `.` 앞에서 나누고, 한 줄에 호출 하나씩 둡니다.
    3. **연산식**(`if` 조건, 대입·`return`의 오른쪽, 연산식인 인자): 연산자 앞에서 나눕니다.
       - 우선순위가 낮은 연산자부터 나눕니다: `||` → `&&` → `? :` → `+`. 같은 연산자끼리는 한 줄에 들어갈 만큼 채웁니다.
       - 안쪽 조각이 어차피 넘쳐도 바깥 연산자 앞에서 먼저 나눕니다.
       - 비교 연산자(`==`, `>` 등) 앞에서는 나누지 않습니다.
       - 여러 줄에 걸친 삼항은 `?`와 `:`를 **둘 다** 줄 맨 앞에 둡니다. 삼항 안의 삼항은 한 줄에 들어가면 그대로 둡니다.
  - **조각**은 연산식의 피연산자, 삼항의 세 부분, 인자 하나(키·값 호출의 값은 키와 함께)입니다. 괄호로 묶인 식과 한 줄에 들어가는 호출(`old.get("clock_in_at")`)도 한 조각입니다.

### 2.2 SQL 위치 이동 (3단계)
- SQL 문자열은 `domain/{도메인}/repository/` 패키지의 클래스에만 둡니다. 예외는 `global/persistence/SqlStore`와 `global/` 공통 쿼리입니다.
  - 서비스·handler·batch 안의 SQL을 옮깁니다.
  - `service/` 패키지에 있는 기존 `*Store`·`*Query`·`*Queries` 클래스는 이름을 그대로 두고 `repository/`로 옮깁니다.
  - `global/` 공통 쿼리는 여러 도메인이 함께 쓰는 세 클래스입니다(`PermissionAccess`, `BatchRunRecorder`, `InvitationTokenStore`). 이번에는 옮기지 않습니다.
- 새로 만드는 클래스 이름: 읽기 위주는 `{도메인}Queries`, 쓰기 위주는 `{도메인}Store`. 메서드 이름은 하는 일을 말합니다(예: `countMonthlyAbsences`).
  - 잠그는 조회(`FOR UPDATE`)는 쓰기를 위한 것이므로 `Store`에 둡니다.
  - 새 클래스는 기존 쿼리 클래스처럼 `@Repository`를 붙입니다.
- **SQL 문자열·파라미터 이름·동적 조각(예: `FOR UPDATE` 붙이기)은 한 글자도 바꾸지 않습니다.** SQL 지문으로 확인합니다.
  - `+`로 만든 SQL 식은 식 전체를 그대로 옮깁니다. 정렬 컬럼처럼 SQL 조각을 고르는 표도 SQL이므로 옮깁니다.
  - 쿼리 메서드는 SQL 파라미터 값을 인자로 받습니다. 값 계산(`LocalDateTime.now(clock)`, `access.actor()`, 요청 값 가공)은 서비스에 남깁니다. 그래야 값을 계산하는 순서와 SQL을 실행하는 시점이 그대로입니다.
- **옮기는 것은 SQL 실행과 결과 받기까지만입니다.** 검증하고 `BusinessException`·`IllegalArgumentException`을 던지는 코드는 서비스에 남깁니다.
  - 주의: `@Repository` 빈은 JPA의 예외 변환을 받습니다. 그래서 그 안에서 던진 `IllegalArgumentException`이나 `IllegalStateException`이 `InvalidDataAccessApiUsageException`으로 바뀔 수 있고, 오류 응답도 달라집니다.
  - 그래서 쿼리 클래스에는 `throw`를 두지 않고, 이런 예외를 낼 수 있는 호출(`Enum.valueOf`, `Integer.parseInt` 같은 파싱)도 두지 않습니다.
  - `db.one(..., ErrorCode)`가 결과가 없을 때 던지는 `BusinessException`은 그대로 옮겨도 됩니다. 변환 대상이 아니고, `SqlStore`가 이미 `@Repository`라 지금과 같은 경로를 지납니다.
  - 오류 응답 스냅샷으로 확인합니다.
- 트랜잭션 경계는 그대로입니다. 쿼리 클래스에 `@Transactional`을 새로 붙이지 않고, 서비스의 `@Transactional` 메서드를 쿼리 클래스로 옮기지 않습니다. 기존 클래스를 패키지만 옮길 때 붙어 있던 것(`ProjectStateStore`의 `MANDATORY`)은 그대로 둡니다.
- 테스트가 스파이로 감싸거나 일부를 바꿔 끼우는 빈(`SqlStore`, `NotificationService`, `AttendanceStore`, `ProjectStateStore`, `PermissionAccess`, `InvitationTokenStore`)은 public 메서드의 이름과 시그니처를 그대로 둡니다. 클래스의 패키지가 바뀌면 테스트는 import만 고칩니다.
- **검증** (커밋마다, 2장의 기록 비교·기록 끈 실행에 더해)
  - `src/main`의 문자열 리터럴·텍스트 블록 **값**(javac가 처리한 값) 집합이 3단계 시작 커밋과 같아야 합니다. 새로 생긴 값은 0이고, 개수가 줄어든 값은 같은 SQL을 한 메서드로 합친 곳뿐이어야 합니다.
    - 왜: SQL 지문은 공백을 압축해 비교하므로, 텍스트 블록 들여쓰기가 어긋나 SQL의 공백이 바뀌어도 잡지 못합니다.
  - `@Transactional`이 붙은 메서드 목록(클래스·메서드·속성)이 시작 커밋과 같아야 합니다. 패키지만 옮긴 클래스는 새 이름으로 대응합니다.
- 리뷰는 2.3과 같은 도메인 묶음 세 번으로 나눠 받습니다.

### 2.3 응답 record · 이름 · 메서드 (4단계)
**응답 record**
- 위치는 `domain/{도메인}/dto/`, 이름은 `{도메인}{동작}ResponseDto`입니다(규칙 문서 4장). 안쪽 구조는 중첩 record로 만듭니다.
- 변환은 **SQL 결과를 지금처럼 `SqlStore`의 행으로 받고, record의 정적 메서드 `from(행)`에서 한 번만** 합니다.
  - 행을 record로 바로 받는 `DataClassRowMapper` 방식은 버립니다. `SqlStore`의 날짜 변환을 거치지 않아 JSON의 날짜 모양이 바뀔 수 있기 때문입니다.
- 필드 타입은 **지금 JSON과 똑같이 나오는 타입**을 고릅니다.
  - DECIMAL은 `BigDecimal`(소수 자릿수 유지), BIGINT는 `long`/`Long`, null이 올 수 있으면 박싱 타입을 씁니다.
  - 지금 `null`로 나가는 키는 record에서도 `null`로 나가야 합니다. 키를 빼면 안 됩니다.
- 컨트롤러 반환 타입은 `ApiResponse<구체 타입>`입니다. 201 같은 상태 코드는 지금처럼 `@ResponseStatus`로 둡니다.
- `SqlStore.map(...)`은 응답을 만드는 데 쓰지 않습니다. SQL 파라미터를 넘길 때만 씁니다.

**이름**
- 한두 글자 변수(`r`, `l`, `x`, `u`, `d`)를 뜻이 드러나는 이름으로 바꿉니다. 루프 인덱스 `i`는 그대로 둡니다. SQL 안의 별칭은 바꾸지 않습니다.
- 컨트롤러·서비스 메서드는 규칙 문서 10.2를 따릅니다(예: `in()` → `clockIn()`). URL은 그대로입니다.

**메서드 나누기**
- 한 메서드가 한 가지 일을 하도록, 의미 단위로 이름 붙은 private 메서드로 나눕니다. 줄 수 기준보다 "이름으로 설명되는가"를 봅니다.
- 주석은 "왜"를 설명하는 것만 남깁니다. 기존의 "왜" 주석은 지우지 않습니다.

**도메인 묶음** (묶음마다 리뷰를 받은 뒤 다음으로 넘어감)
1. org · user · permission
2. approval · leave · overtime
3. attendance · calendar · home · notification · project · task · dashboard
