# 문제 찾기 — M6 (가상 회사 데이터와 시나리오 부하)

> 기준: [16-deploy-ops-m5.md](16-deploy-ops-m5.md)의 서버와 관측 도구. 배포와 작은 데이터 기준값 측정이 끝난 뒤에 시작합니다.
> 목표: 실제 회사가 이 시스템을 몇 년 쓴 상황을 정해 놓고, 사용자가 겪을 증상을 직접 재현합니다. 재현된 것만 원인을 좁혀 고치고 같은 조건으로 전후를 잽니다.
> 문제가 안 나오면 안 나왔다고 기록합니다. 데이터나 부하를 부풀려 문제를 만들지 않습니다.

## 0. 결정

| 결정 | 이유 · 버린 것 |
|---|---|
| **기준 회사 S1: 재직 300명, 5년 사용** | 중소기업 그룹웨어로 현실적인 규모. 명세 16의 1,000명은 이 회사가 성장한 뒤의 상황으로 옮김 |
| **확장 회사 S2: 계열사 700명이 합류해 1,000명, 합류 후 1년** | 2년 만에 3배로 성장하는 것보다 하루아침에 사용자가 늘어나는 이유로 자연스러움. S1에서 문제가 없어도 "어디서 먼저 깨지는가"를 볼 수 있음 |
| **회사 유형: IT·서비스 회사** | 프로젝트·업무 보드를 쓰는 사무직 중심 회사. 제조업의 교대 근무는 출근 패턴이 완전히 달라 이번 범위에서 뺌 |
| **결과를 바꾸는 가정만 현실에 가깝게** | 모든 것을 현실처럼 만들면 생성기가 별도 프로젝트가 됨. 나머지는 단순하게 둠 |
| **합성 데이터, 고정 시드** | 실제 회사 자료가 없고, 전후 비교를 같은 데이터로 해야 함. 포트폴리오에도 합성 데이터라고 밝힘 |
| **측정마다 스냅샷 복원** | 쓰기 시나리오가 데이터를 바꾸므로 같은 출발점이 필요함 |
| **부하 도구는 k6, 로컬 PC에서 실행** | 서버에 올리면 2 GiB와 CPU를 나눠 쓰게 됨. 목표 부하가 초당 수십 건이라 PC 한 대로 충분함. nGrinder는 설치 부담이 큼 |
| **서버는 명세 16의 t3.small, 크레딧 standard 그대로** | 질문은 "이 서버로 버티는가"임. 증설은 해결책 후보 중 하나로만 다룸 |
| **판정 기준을 측정 전에 고정** (6장) | 결과를 보고 기준을 바꾸는 일을 막음. 바꿀 때는 이유를 기록 |
| **증상 → 원인 → 대안 → 수정 순서** | 기술을 먼저 고르지 않음. Redis 캐시, 검색 엔진, 메시지 브로커를 처음부터 답으로 두지 않음 |
| **한 번에 문제 하나만 수정** | 여러 개를 함께 고치면 어떤 수정이 효과를 냈는지 알 수 없음 |

## 1. 가상 회사

포트폴리오 글의 무대입니다. 가상 회사라는 사실은 숨기지 않습니다.

| 항목 | S1 기준 회사 | S2 확장 회사 |
|---|---|---|
| 업종 | IT·서비스, 사무직 중심 | 같음 |
| 기간 | 측정일 기준 최근 5년 | 최근 6년 (5년은 300명, 계열사 합류 뒤 1년은 1,000명) |
| 재직자 | 300명 | 1,000명 |
| 누적 퇴사자 | 약 150명 (연 10%) | 약 250명 |
| 부서 | 20개, 깊이 3단계 | 50개, 깊이 3단계 |
| 근무제 | 09:00~18:00 기본, 부서 3개는 시차 출근 | 같음, 부서 8개 시차 출근 |
| 사람 수로 본 누적 근무 | 1,500인·년 | 2,500인·년 |

계열사는 본사 아래 한 부문으로 편입합니다. 시스템이 회사 하나만 지원하기 때문입니다. 계열사의 과거 기록은 옮기지 않고 합류일부터 쌓습니다.

회사에서 부하가 몰리는 때는 다음과 같습니다.

- 평일 08:50~08:58 출근
- 월말 근태 마감일 오후, 월말 지출결의
- 부서장의 월요일 오전 결재
- 12월 연차 사용, 1월 연차 부여
- 업무 시간 내내 화면을 켜 둔 상태

분포와 사건은 측정 결과를 바꾸는 것만 현실에 가깝게 정합니다. 근거가 없는 값은 "가정"으로 표시하고, 주변 직장인 인터뷰로 확인되면 근거를 바꿉니다.

| 항목 | 정하는 방식 | 근거 |
|---|---|---|
| 출근 | 근무일의 95% 출근, 4% 휴가, 1% 이하 결근 | 가정 |

| 결재선 | 결재자 평균 2명, 참조 30% | 가정 |
| 결재 쏠림 | 규칙대로 부서장·상위 부서장에게 몰림. 지출결의는 재무 담당과 대표까지 감 | 가정 |
| 결재 상태 | 승인 90%, 반려 5%, 회수 3%, 진행 중 2% (진행 중은 최근 문서만) | 가정 |
| 시기 몰림 | 지출결의는 월말, 연차 사용은 12월, 연차 부여는 1월 | 가정 |
| 연차 | 1년 미만 월 1일, 이후 15일, 2년마다 1일 가산, 최대 25일 | 근로기준법 |
| 공휴일 | 실제 공휴일과 대체공휴일 | 실제 달력 |
| 조직 변화 | 연 1회 부서 개편, 부서장 공석 기간, 퇴사자에게 걸린 결재, 동명이인 | 가정 |
| 문서 제목 | 양식별 사전 + 프로젝트명 + 월. "○월 법인카드 사용 내역"처럼 반복되는 제목 포함 | 가정 |
| 알림 | 90% 읽음, 안 읽은 알림은 최근에 몰림 | 가정 |
| 화면 켜 둠 | 업무 시간 중 재직자 전원 (SC-4의 상한) | 가정 (인터뷰로 확인) |

단순하게 둔 것: 도입 초기의 낮은 사용량, 업무 이력의 세부 내용, 모바일 사용 비율. 시나리오 결과를 크게 바꾸지 않는다고 보고 균일하게 생성합니다.

## 3. 데이터 생성기 (`deploy/synth/`, Codex)

```
deploy/synth/README.md
deploy/synth/generate.py      프로필·시드·as-of 날짜로 CSV 생성 (Python 표준 라이브러리만)
deploy/synth/validate.py      불변식 검사와 분포 보고
deploy/synth/profiles.json    S1, S2 산식
deploy/server/restore-snapshot.sh
```

- 일회용 로컬 MariaDB 10.11 컨테이너에 Flyway V1~V6를 적용하고, CSV를 넣은 뒤 덤프해 스냅샷을 만듭니다.
- 개발 DB(`mini-erp-dev-mariadb`)는 쓰지 않습니다. 스냅샷은 저장소 밖 `~/workflow-synth/`에 둡니다.
- 입력은 `--profile`, `--seed`, `--as-of`입니다. 같은 입력이면 같은 데이터가 나와야 합니다.
- `--as-of`는 측정일 전 7일 이내의 날짜로 잡습니다. 그 뒤 날짜의 기록은 만들지 않습니다.

`validate.py`는 다음을 확인합니다.

- 외래 키와 UNIQUE 위반 0건, 표별 행 수는 산식의 ±5% 이내
- 승인된 문서에 대기 중 결재선이 없음, 결재 차례와 상태가 일치
- `doc_no_sequences`와 `login_id_sequences`가 최댓값 이후를 가리킴 (새 기안이 충돌하지 않음)
- 연차 원장 합계가 음수가 아님, 재직 기간 밖에는 근태 기록이 없음
- 연차 부여량이 법정 규칙과 일치, 공휴일이 실제 달력과 일치
- 근태 판정값이 현재 판정 규칙과 일치
- 앱을 띄워 표본 사용자로 주요 API가 200을 반환함

## 4. 시나리오

S1에서 전부 돌린 뒤 S2로 넘어갑니다. "내부 가설"은 무엇을 볼지 정하는 메모이며 포트폴리오에는 쓰지 않습니다. 포트폴리오는 실제로 생긴 일로 시작합니다.

| ID | 사용자 상황 | 부하 (S1 / S2) |
|---|---|---|
| SC-1 | 아침에 출근 버튼과 홈을 함께 쓴다 | 피크 초당 9건 / 30건, 15분 재현 |
| SC-2 | 월말에 근태 화면과 CSV를 연다 | 전 직원이 10분 안에 1회 + 부서장·인사 담당 |
| SC-3 | 예전 결재 문서를 검색한다 | 동시 1, 5, 20명 |
| SC-4 | 화면을 켜 두고 일한다 | 초당 15건 / 50건, 60분 유지 |
| SC-5 | 데이터가 쌓이고 서버를 재시작한다 | 부하 없음, 측정 위주 |
| SC-6 | 하루 종일 로그인한 채 일한다 | 실제 브라우저 단건 재현 |

### SC-1 아침 출근

- 사용자별 요청: `GET /home`, `GET /attendance/today`, `POST /attendance/clock-in`, `GET /notifications/unread-count`, `GET /approval-inbox/counts`
- 재전송 변형: 5% 사용자가 응답을 못 받은 상황을 흉내 내 1~3초 뒤 같은 출근 요청을 다시 보냅니다.
- 볼 것: API별 p50·p95·p99, 5xx 비율, 재전송 사용자가 받은 응답, 잠금 대기, Hikari 대기, 크레딧
- 내부 가설: 재전송은 오류로 돌아와 사용자에게 실패처럼 보입니다. 출근은 사용자 행을 잠그고 그 안에서 휴일·휴가를 조회합니다.
- 더 파볼 질문: 사람+날짜가 이미 유일 키이므로 별도 멱등 키가 필요한가? 사용자 행 잠금은 무엇과의 순서를 지키는가? 잠금 안의 조회를 밖으로 빼도 안전한가?

### SC-2 월말 근태

- 전 직원이 10분 안에 `GET /attendance/me?month=` 1회, 부서장은 `GET /attendance/monthly`, 인사 담당 3명은 전사 월간과 `GET /attendance/monthly/export`
- 순간 몰림 변형: 같은 요청을 동시 20명
- 볼 것: 요청당 SQL 수, p95, 읽은 행, CSV 시간, DB CPU
- 내부 가설: 내 월간 근태는 날짜마다 휴일·휴가를 조회해 한 번에 60회가 넘습니다.
- 더 파볼 질문: 전사 공통이고 거의 안 바뀌는 휴일을 매번 DB에서 읽어야 하는가? 마감된 지난달은 정정 결재가 있을 때만 바뀌는가?

### SC-3 결재 검색

- `GET /approval-inbox?box=&q=&page=&size=`
- 사용자 3종: 일반 직원, 문서가 많은 부서장, 넓은 범위 권한자(해당 화면이 있을 때)
- 검색어 3종: 제목 일부, 문서번호 앞부분, 결과가 없는 단어. 첫 페이지와 뒤쪽 페이지를 함께 잽니다.
- 볼 것: p95, `ANALYZE FORMAT=JSON`의 읽은 행과 실제 인덱스, COUNT 쿼리 비용
- 내부 가설: 앞뒤 `%` LIKE라 제목 인덱스를 못 탑니다. 다만 일반 사용자는 결재선 인덱스로 먼저 좁혀져 문제가 없을 수 있습니다.
- 더 파볼 질문: 문제가 넓은 범위 검색에만 있는가? 문서번호 형태 검색어는 앞부분 일치로 분기할 수 있는가? 기본 기간 제한이 인덱스보다 나은가?

### SC-4 화면을 켜 둔 상태

- 화면은 60초마다 API 3개(`/approval-inbox/counts`, `/approval-inbox?box=todo`, `/notifications/unread-count`)를 호출합니다.
- S1 300명 × 3 / 60초 = 초당 15건, S2 1,000명 = 초당 50건. 명세 16의 평소 부하 가정(초당 10건)에는 이 호출이 들어 있지 않습니다.
- 60분 유지하며 `CPUCreditBalance`의 기울기를 봅니다.
- 내부 가설: S2에서는 자동 갱신만으로 기준 성능(0.4 vCPU)을 넘어 크레딧이 줄어들 수 있습니다.
- 더 파볼 질문: 쿼리를 빠르게 하는 것과 호출 자체를 줄이는 것 중 무엇이 효과가 큰가? 안 보는 탭 중단, 변경 없을 때 304, 호출 합치기, 주기 조정을 비교합니다.

### SC-5 데이터 증가와 재시작

- 표별 데이터·인덱스 크기, 버퍼 풀 적중률, 재시작 직후 첫 요청 지연과 회복 시간
- 백업과 복구 시간(명세 16 기준값과 비교), 야간 배치(`batch_runs`)의 실행 시간
- 내부 가설: 512 MB 버퍼 풀을 넘으면 콜드 상태에서 체감이 커질 수 있습니다. 알림은 규칙상 수십만 건이라 저장 문제는 작을 수 있습니다.

### SC-6 하루 종일 로그인

- 액세스 토큰은 1시간이고 재발급이 없습니다. 만료되면 화면이 로그인 페이지로 이동합니다.
- 실제 브라우저로 1시간을 넘겨 일반 화면과 결재 작성 중 화면에서 어떤 일이 생기는지 확인합니다.
- 내부 가설: 근무 중 1시간마다 로그아웃되고 작성 중인 내용이 사라질 수 있습니다.
- 더 파볼 질문: 토큰 무효화(`TOKEN_REVOKED`)를 이미 서버에서 확인한다면 긴 토큰의 단점이 줄어드는가? 리프레시 토큰, 활동 기반 연장, 긴 수명 토큰을 비교합니다.

| 항목 | 규칙 |
|---|---|
| 출발점 | 측정마다 스냅샷 복원 → 앱 재시작 → 같은 요청으로 예열 |
| 크레딧 | 시작 시 `CPUCreditBalance` 120 이상. 시간당 24가 쌓이므로 0에서 약 5시간 필요. 크레딧 소진 동작을 보는 실험은 별도 표시 |
| 반복 | 시나리오·조건별 3회, 중앙값과 범위 기록 |
| 시간대 | 야간 배치(00:10)와 마감 알림(09:00 KST) 주변은 피함 |
| 같이 기록 | 커밋, 스냅샷 이름, 측정 시각, 크레딧 시작·끝, 서버 가동 시간 (`measure-context.sh`) |
| 느린 쿼리 | 측정 중 `long_query_time=0.2`, 끝나면 되돌림 |
| 요청당 SQL 수 | 단일 사용자로 일반 로그를 잠깐 켜서 세거나 Testcontainers 기록으로 셈 |
| Hikari 대기 | 실험 동안만 `metrics`를 127.0.0.1:8081에 노출, 끝나면 되돌림 |

## 6. 문제 판정 기준

측정 전에 고정합니다. 우리가 정한 기준이라고 글에도 밝힙니다.

| 대상 | 문제로 보는 조건 |
|---|---|
| 화면 조회 API | p95 1초 초과 |
| 출근·결재 등 쓰기 API | p95 1초 초과 |
| CSV 내려받기 | p95 5초 초과 |
| 오류 | 5xx 0.1% 초과 |
| 사용자에게 실패로 보이는 응답 | 실제로는 성공했는데 오류를 받는 경우 1건이라도 |
| CPU 크레딧 | 업무 9시간을 못 버티는 감소 속도 |
| 메모리 | 측정 중 swap 사용량이 계속 증가 |
| 재시작 | 예열 없는 첫 화면이 3초 초과 |

## 7. 원인 좁히기

1. Nginx 로그와 `slow-endpoints.sh`로 느린 API를 찾습니다.
2. 느린 쿼리 로그와 `mariadb-dumpslow`로 쿼리를 찾습니다.
3. `EXPLAIN`과 `ANALYZE FORMAT=JSON`으로 예상과 실제 행 수를 비교합니다. MariaDB 10.11이므로 MySQL 8의 `EXPLAIN ANALYZE`는 쓰지 않습니다.
4. `Handler_read_%`, `Innodb_buffer_pool_reads`, `Innodb_row_lock_time`을 전후로 잽니다.
5. 잠금은 `SHOW ENGINE INNODB STATUS`와 `information_schema.INNODB_LOCK_WAITS`로 확인합니다.
6. 확인하지 못한 설명은 "추정"이라고 씁니다. MySQL 8 사례의 결론을 그대로 가져오지 않습니다.

## 8. 고치는 절차

문제 하나마다 브랜치 하나로 진행합니다.

1. **증상**: 어떤 사용자가 어떤 상황에서 무엇을 겪는가
2. **재현**: 수정 전 명령과 수치
3. **원인**: 7장의 근거
4. **당연한 답부터 검토**: 가장 먼저 떠오르는 해결책과 그것이 부족한 이유
5. **대안 비교**: 2개 이상. 효과, 쓰기 비용, 정합성, 권한, 운영 복잡도, 요금
6. **수정**: 가장 단순한 방식부터
7. **재측정**: 같은 스냅샷과 조건으로 3회
8. **부작용 확인**: 쓰기 시간, 응답 동등성, 권한 조건, 캐시 무효화

권한 조건을 건드리는 수정은 권한 없는 사용자와 조건이 꺼진 경로까지 테스트합니다.

## 9. 비용 판단

쿼리 수 감소를 요금 절감으로 쓰지 않습니다. 현재 구조는 요금이 고정이므로 "어떤 등급이 필요한가"로 판단합니다.

| 질문 | 근거 |
|---|---|
| t3.small로 S1·S2의 피크와 하루 사용을 버티는가 | SC-1, SC-4의 크레딧과 p95 |
| 개선 전후로 필요한 서버 등급이 달라지는가 | 같은 부하의 CPU 사용량과 크레딧 기울기 |
| 저장소 30 GiB로 몇 년을 쓰는가 | SC-5의 증가량과 백업 크기 |
| 새 구성요소를 넣으면 무엇이 늘어나는가 | 메모리 예산과 서버 등급 |

실험 비용은 켜 둔 시간당 약 $0.031(t3.small + 공인 IPv4)입니다.

## 10. 역할과 안전

| 담당 | 할 일 |
|---|---|
| 사용자 | AWS 인스턴스 켜기·끄기, 크레딧 확인, 합성 계정 비밀번호 입력(숨김 입력) |
| Codex | 생성기, 검증기, k6 스크립트, 수집 스크립트, 확정된 문제의 수정 |
| Claude | 명세, 리뷰, 실험 실행, 분석 |

- 서버에는 합성 데이터만 넣습니다. 복원 스크립트는 서버에 합성 데이터 허용 표시 파일이 없으면 멈춥니다.
- 합성 계정 비밀번호는 환경 변수로만 받습니다. 저장소, 명령 인자, 로그, 채팅에 남기지 않습니다. k6 토큰은 메모리에만 둡니다.
- 합성 사용자 메일은 `.invalid` 도메인을 쓰고 메일 발송은 끈 상태를 유지합니다.
- 실험 전후 백업을 로컬로 받습니다. 실험이 끝나면 합성 계정을 지우거나 서버를 끕니다.
- 시크릿과 스냅샷은 커밋하지 않습니다. `git add .`는 쓰지 않습니다.

## 13. 하지 않는 것

| 하지 않음 | 이유 |
|---|---|
| 재현 전 수정 | 전후 비교가 사라짐 |
| 데이터나 부하를 부풀려 문제 만들기 | 가정한 회사와 맞지 않음. S2를 넘는 규모가 필요하면 이유를 먼저 적음 |
| Kafka, Elasticsearch, 읽기 복제, MSA 선도입 | 측정 근거가 없음. 2 GiB 서버에서는 운영도 어려움 |
| 결재·채번·출근 중복 동시성 재작업 | M2~M4에서 재현하고 고침. 새 증상이 나올 때만 다룸 |
| 결재 위임 같은 새 기능 | 이번 단계는 문제 찾기. 필요하면 따로 결정 |
| GC·DB 설정을 근거 없이 조정 | 측정으로 원인이 확인될 때만 |
| 실제 회사 데이터나 실제 고객처럼 꾸미기 | 합성 데이터임을 밝힘 |
