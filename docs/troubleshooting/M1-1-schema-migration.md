# M1-1 — 스키마·기존 데이터 이관

## 증상
고정 부서 코드·단일 역할 컬럼으로는 조직 트리와 복수 역할을 표현할 수 없다. 기존 is_active에는 비활성 사유가 없고 입사일도 없다.

## 재현 방법
M1DataMigrationTest는 MariaDB 10.11에 V1만 적용하고 기존 세 부서·세 역할·같은 직급·숫자 아이디·비활성 사원을 넣은 뒤 V2를 적용한다. MariaDbMigrationTest는 빈 DB의 Flyway/validate와 제약 조건을 검사한다.

## 원인
users에 부서·직급·역할이 직접 저장되어 있다. v1에는 is_active를 false로 바꾸는 기능이 없어 수동 변경 사유를 알 수 없다. 휴직과 퇴사를 구분할 근거가 없다.

## 검토했지만 버린 방법과 이유
V1 수정이나 DB 재생성은 기존 M0 데이터 보존 요구에 어긋난다. ON_LEAVE는 복귀할 사람이라는 의미인데 그 근거가 없어 선택하지 않는다. 과거 입사일을 임의로 만들어 넣지 않는다.

## 선택한 방법
2026-10-15 사용자 결정에 따라 is_active=false는 가장 제한적인 RETIRED로 이관한다. 필요하면 관리자가 상태 변경 API로 복원한다. 기존 hire_date는 NULL로 보존하고 새 등록에서만 날짜를 필수로 받는다. PATCH 보정은 M1-10 문서에 설명한다.

V2에서 새 테이블·초기 권한을 만들고 기존 이름/아이디/연차/암호값을 보존한 뒤 구 컬럼을 삭제한다. 기존 숫자 아이디의 최댓값은 이관 시 연도별 시퀀스 초깃값에만 사용하며 실제 등록은 행 잠금으로 발급한다. 기본 근무시간/루트의 유일성은 가상 열·유니크 인덱스로 보장한다. 모든 인덱스에 사용 조회를 주석으로 남겼다.

비활성 이관 UPDATE 직후 SQL SELECT가 `M1: migrated_inactive_to_retired=N`을 반환한다. Flyway INFO 실행 로그에 결과가 남으며 사용자·비밀번호는 출력하지 않는다. 적용 당시 건수를 남기려면 앱 기동 로그를 보관한다. 이후 상태를 복원한 현재 RETIRED 행 수와 이 역사적 건수는 다를 수 있다.

## 부작용·남은 위험
MariaDB DDL은 자동 커밋하므로 실제 적용 전 백업 및 복제 DB 리허설이 필요하다. 기존 부서 코드가 01/02/03 외의 값이면 먼저 데이터를 확인해야 한다. 모든 기존 관리소장이 비활성인 DB는 복원할 관리자 접근 경로를 이관 전에 점검해야 한다. 이관 자체가 새 관리소장을 임의로 승격하지는 않는다.

## 결과
M1DataMigrationTest에서 활성 2명/비활성 1명은 ACTIVE 2명/RETIRED 1명으로 이관되고 입사일은 전부 NULL이다. 기존 역할·부서·직급·아이디·연차·암호값 보존 및 이관 로그의 `migrated_inactive_to_retired=1`을 확인했다. 빈 DB 로그는 0이며 V1 → V2와 Hibernate validate, 외래키 20개 및 유니크 제약 검증도 통과했다. V1과 설계 문서는 수정하지 않았다.
