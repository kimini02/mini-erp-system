# M1 P2-1 — 사원별 초대 토큰 수명 관리

> 후속 변경: 이메일 변경 시 폐기는 이제 커밋 뒤에 수행한다. 현재 동작과 롤백·이메일 바인딩 검증은 `M1-14-invitation-after-commit.md`를 따른다. 아래 내용은 최초 수정 당시 기록이다.

## 증상
초대를 재발송하거나 사원 이메일을 변경한 뒤에도 이전 수신자가 링크로 비밀번호를 설정할 수 있었다.

## 재현 방법
Java 17 + Docker에서 `cd backend` 후 `./mvnw -Dtest=InvitationLifecycleTest test`.
실제 MariaDB 10.11과 Redis 7.4 테스트 컨테이너를 사용하며 메일 발송기만 가짜로 대체한다.
링크 A 발송 → 이메일 수정 → 재발송 → A로 비밀번호 설정 순서에서 기대한 401 대신 200이 반환됐다.
이메일만 변경, 재발송만 수행한 경우도 같은 문제였다. 동시 발급한 토큰 8개가 모두 사용 가능했다.

## 원인
Redis에 토큰 → 사원 매핑만 저장하고 사원별 현재 토큰을 관리하지 않았다. 이메일 변경 경로에서 토큰을 폐기하지 않았다.
커밋 뒤 발송 이벤트는 발행 당시 이메일만 사용하므로 뒤늦게 실행되면 과거 이메일로 유효한 새 토큰을 보낼 수 있었다.

## 검토했지만 버린 방법과 이유
- 이전 토큰이 자연 만료될 때까지 기다림: 유효기간 24시간 동안 이전 수신자의 접근을 허용한다.
- Redis 키를 따로 조회·삭제·저장: 동시 재발송과 소비 사이에 경쟁 구간이 남는다.
- DB 커밋 뒤에만 이메일 변경에 따른 토큰 폐기: 커밋과 폐기 사이에 이전 링크가 사용될 수 있다.
- 새 라이브러리 또는 별도 저장소: 기존 Spring Data Redis와 MariaDB 잠금으로 처리 가능하다.

## 선택한 방법
- 사원별 현재 토큰 키와 토큰별 사원 키를 24시간 TTL로 함께 저장한다. Lua로 교체·소비·폐기를 각각 원자적으로 처리한다.
- 재발송 요청과 이메일 변경은 사용자 행을 잠그고 이전 토큰을 폐기한다. 이메일이 그대로면 폐기하지 않는다.
- 비밀번호 설정은 토큰의 소유자를 조회해 사용자 행을 잠근 다음, 현재 토큰인지 다시 확인하면서 소비한다. 소유자 조회만으로 인증하지 않는다.
- 커밋 뒤 발송은 별도 트랜잭션에서 사용자 행을 잠그고 현재 이메일 및 비밀번호 미설정 여부를 확인한다. 과거 이메일 이벤트는 발송하지 않는다.
- 배포 전 형식의 토큰은 현재 토큰 키가 없으므로 사용할 수 없다. 필요하면 재발송한다.

## 부작용·남은 위험
- DB와 Redis는 하나의 분산 트랜잭션이 아니다. 이메일 변경이 나중에 롤백되거나 비밀번호 저장이 실패하면 이미 폐기·소비된 링크는 복구하지 않는다. 재발송이 필요하지만 이전 링크가 되살아나지는 않는다.
- Redis 폐기에 실패하면 이메일 변경·재발송 트랜잭션도 실패시킨다. 무효화를 보장하지 못한 채 성공 응답을 주지 않는다.
- 발송 시 사용자 잠금은 SMTP 호출 동안 유지된다. 메일이 느리면 같은 사원의 변경이 기다릴 수 있다. 사원 등록 자체는 이미 커밋된 상태다.
- 기존 단일 Redis 운영 구성을 사용한다. 토큰이나 메일 본문을 로그에 추가하지 않았다.

## 결과
- 수정 전 `InvitationLifecycleTest`: 5개 중 5개 실패, 오류·건너뜀 0.
- 수정 후 같은 테스트: 5개 모두 성공. 동시 발급 8개 중 사용 가능한 토큰은 1개.
- 기존 `M1AcceptanceTest`와 함께 실행: 총 35개, 성공 35개, 실패·오류·건너뜀 0.
- 검증: 이전 링크 401 SETUP_TOKEN_INVALID, 최신 링크 최초 200·재사용 401, 이메일 변경만으로 폐기, 재발송만으로 폐기, 과거 이메일 이벤트 무시, 실제 Redis 동시 교체.
- 기존 가짜 토큰 저장소도 단일 유효 토큰 계약에 맞게 수정했다.
