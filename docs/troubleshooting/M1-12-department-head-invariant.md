# M1 P2-2 — 부서장 소속·재직 불변식

## 증상
부서장 지정과 사원의 부서 이동·퇴사·휴직이 겹치면 다른 부서 소속이거나 비재직인 사원이 부서장으로 남을 수 있었다.

## 재현 방법
Java 17 + Docker에서 `cd backend` 후 `./mvnw -Dtest=DepartmentHeadConcurrencyTest test`.
MariaDB 10.11의 실제 두 트랜잭션을 사용한다. SQL 실행 결과와 잠금은 대체하지 않고, 테스트 스파이와 래치로 실행 순서만 조절한다. 권한 검사는 별도 M1AcceptanceTest가 검증하며 여기서는 잠금 경쟁에 집중한다.

1. 사원 변경이 부서장 여부를 확인한 뒤 UPDATE 직전에 대기한다. 다른 트랜잭션에서 부서장으로 지정한 뒤 사원 변경을 진행한다.
2. 사원 변경 트랜잭션이 먼저 부서장 없는 상태의 REPEATABLE READ 스냅샷을 만든다. 다른 트랜잭션이 부서장 지정을 커밋한 뒤 사원 변경을 진행한다.
각 순서를 부서 이동, RETIRED, ON_LEAVE에 대해 3회씩, 총 18회 실행한다.

## 원인
OrgService는 조직 루트 행을 잠갔지만 EmployeeService.patch와 status는 같은 잠금을 잡지 않았다. 부서장 확인과 사용자 변경 사이에 부서장 지정이 끼어들 수 있었다.
또한 부서장 검사가 일반 COUNT 조회라서 MariaDB REPEATABLE READ의 과거 스냅샷을 읽을 수 있었다. 트리 잠금만 추가해도 이미 열린 스냅샷 문제는 남는다.

## 검토했지만 버린 방법과 이유
- 화면에서 부서장 여부 확인: 동시에 도착하는 서버 요청을 막지 못한다.
- 트리 잠금만 추가: 기존 트랜잭션의 스냅샷이 갱신되지는 않는다.
- 사용자 행만 잠금: OrgService와 동일한 조직 변경 잠금 순서를 보장하지 못한다.
- 트랜잭션 격리 수준을 전역 변경하거나 재시도만 추가: 다른 기능에 영향을 주며 불변식을 보호하는 잠금 규칙이 드러나지 않는다.

## 선택한 방법
- 기존 루트 행 잠금을 DepartmentTreeLock으로 모으고 OrgService와 EmployeeService가 함께 사용한다. 반드시 기존 트랜잭션 안에서 호출하도록 MANDATORY를 지정했다.
- 부서 지정이 포함된 patch, 비재직 상태로의 status는 가장 먼저 트리 잠금을 획득한다. 이후 기존 권한 검사와 필요한 역할·사용자 잠금을 수행한다.
- 변경 대상 사용자는 FOR UPDATE로 현재 값을 읽는다. 부서장 여부도 `SELECT id FROM departments WHERE head_user_id=:id FOR UPDATE`로 확인한다.
- 부서장으로 먼저 지정됐으면 HEAD_MUST_BE_REASSIGNED로 사원 변경을 거부한다. 사원 변경이 먼저 끝났으면 setHead의 기존 소속·ACTIVE 검증이 지정을 거부한다.

## 부작용·남은 위험
- 조직 트리 변경과 부서·비재직 상태 변경은 루트 행에서 직렬화된다. 기존 단일 회사 규모에 맞춘 잠금이며 조직 변경이 잦아지면 대기 시간을 측정해야 한다.
- 부서와 이메일을 함께 바꾸면 트리 → 사용자 순서다. 비재직 전환은 트리 → CHIEF 역할 → 사용자 순서이고, 부서장 지정은 트리 → 사용자 순서다.
- 애플리케이션 경로의 불변식을 보호한다. 직접 SQL로 잘못된 부서장을 지정하거나 이전부터 존재하던 잘못된 데이터를 자동 복구하는 작업은 포함하지 않는다.
- 스키마, V1, 설계 명세, 프론트엔드 및 라이브러리는 변경하지 않았다.
