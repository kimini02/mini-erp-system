# M1-4 — 조직·사원·역할 API와 초대

## 증상
조직·사원·역할·공휴일을 관리할 API 및 초대 비밀번호 설정이 필요하다. 동시에 등록하면 단순 MAX+1은 충돌한다.

## 재현 방법
M1AcceptanceTest 전체를 실행한다. concurrentIdAllocationIsUniqueAndUnsafeMaxPlusOneCollides는 실제 스레드를, organizationTreeAlwaysUsesTwoBusinessQueries는 MariaDB Com_select 세션 카운터를 사용한다.

## 원인
등록 번호 조회/저장을 분리하면 같은 번호를 가져간다. 초대 메일을 트랜잭션 안에서 보내면 롤백된 계정으로 링크를 보낼 수 있다.

## 검토했지만 버린 방법과 이유
MAX+1: 동시 두 등록 중 한 건이 유니크 충돌하는 것을 재현했다. AUTO_INCREMENT만 사용하면 연도별 순번 요구를 만족하지 못한다. 메일 발송 실패로 사용자 등록을 되돌리지 않는다.

## 선택한 방법
입사연도별 시퀀스를 SELECT FOR UPDATE로 잠그고 등록·역할 저장을 함께 커밋한다. AFTER_COMMIT 이벤트가 메일을 보내고 성공 여부를 응답에 반영한다. 초대 토큰은 Redis에 24시간 보관하고 원자적으로 소비한다. 서로 다른 초대 링크를 동시에 써도 첫 설정만 허용하도록 사용자 행도 잠근다. 이 경쟁은 수정 전 두 요청 성공, 수정 후 하나만 성공으로 검증했다.

## 부작용·남은 위험
명세에 없는 결재 양식 테이블/규칙은 만들지 않았다. 역할 삭제의 결재 규칙 사용 여부는 M2에서 연결해야 한다. 근무시간 변경에 대한 과거 근태 스냅샷은 M3 범위이다. 조직도 인원수의 재직 상태 필터는 명세에 없어 전체 소속 사원을 센다. 사용자 정의 역할 코드는 서버가 R-번호로 발급한다.

## 결과
8개 스레드 안전 발급은 중복 0건. 조직도는 부서 4개/16개 모두 SELECT 2번. 메일 끔/실패/롤백, 커밋 뒤 발송, 한 번 사용, 강제 비밀번호 변경, 부서 순환, 공휴일 중복, 사원 검색·탭 집계·기존 응답 필드를 확인한다.
