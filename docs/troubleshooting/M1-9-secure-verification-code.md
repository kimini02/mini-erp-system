# M1-9 — 비밀번호 재설정 인증번호 SecureRandom

## 증상
인증번호를 암호용으로 설계되지 않은 java.util.Random으로 생성했다.

## 재현 방법
`AuthVerificationCodeTest.resetUsesSecureRandomAndKeepsSixDigitCodeInStoreAndMail`은 암호학적 난수 공급자를 실제로 사용하는지와 6자리 범위 양 끝, 저장·메일의 동일 코드 전달을 검사한다. 수정 전 SecureRandom 생성/사용이 없어 실패했다. 실제 계정의 인증번호 예측 공격을 실행한 테스트는 아니다.

## 원인
Random은 48비트 내부 상태를 사용하는 결정적 선형 합동 생성기이며 암호학적 예측 저항성을 제공하지 않는다. 내부 상태나 시드를 알면 이후 출력도 계산할 수 있어 인증 자격을 확인하는 값에 적합하지 않다. 매번 새 Random을 만드는 것도 이 설계를 바꾸지 않는다.

## 검토했지만 버린 방법과 이유
시간 기반 시드를 수동으로 넣거나 ThreadLocalRandom으로 바꾸는 방법은 암호학적 난수가 아니다. 출력 중복 여부를 통계적으로 검사하는 테스트도 보안성을 증명하지 못한다.

## 선택한 방법
JDK의 SecureRandom을 AuthService에서 재사용하며, 직접 시드를 지정하지 않고 기본 보안 제공자의 초기화를 사용한다. 기존 범위 `100000 + nextInt(900000)`와 저장·메일 흐름은 유지한다. 새 라이브러리를 추가하지 않는다.

## 부작용·남은 위험
6자리 인증번호의 경우의 수, 만료 시간과 요청 제한은 그대로다. 이 변경은 난수 예측 위험을 줄이며 무차별 대입 등 모든 공격을 해결하는 것은 아니다. 기존 인증번호 로그 문제는 별도 이슈로 남아 있고 이번 변경에서 손대지 않는다.

## 결과
수정 전 보안 공급자 검증 실패 → 수정 후 1개 테스트 통과. 가짜 SecureRandom의 경계값으로 저장소와 메일에 100000/999999가 동일하게 전달됨을 확인했다. 엔트로피나 제공자 구현 자체의 안전성을 이 테스트로 증명한다고 주장하지 않는다.
