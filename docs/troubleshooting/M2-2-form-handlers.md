# M2-2 — 공통 결재와 양식 처리기

## 증상
기존 특근 요청은 overtimeDate를 보내도 서버가 startDate/endDate를 읽어 실패했다. 휴가 구현도 approval 패키지에 직접 들어 있어 공통 결재에 다른 양식을 붙이기 어려웠다.

## 재현 방법
기존 CoreApiIntegrationTest.approveOvertime_shouldReturnApprovedStatus가 KI-01 때문에 비활성화되어 있었다. 새 계약의 임시 저장 → 상신 → 승인으로 해당 테스트를 복구하고 MariaDB Testcontainers로 실행한다.

## 원인
특근 요청의 날짜 계약이 불일치했고 결재 상태와 양식별 업무가 한 구현에 섞여 있었다.

## 검토했지만 버린 방법과 이유
옛 특근 DTO만 고치는 방식은 새 결재 문서와 양식 분리 요구를 충족하지 않는다. 결재 서비스에서 휴가·특근을 직접 호출하는 방식도 새 양식마다 결재 코드를 바꿔야 하므로 사용하지 않는다.

## 선택한 방법
ApprovalFormHandler의 validate/onSubmitted/onApproved/onRejected/onWithdrawn을 동기로 호출한다. 본문 형식 검사·저장·복사·조회도 같은 인터페이스에 두어 결재 서비스가 업무 구현을 알지 않게 했다. 휴가는 leave 패키지로 이동했고, 일반 품의는 approval.general에 둔다. 날짜·시간·필수값은 임시 저장에서 검사하고 잔여·중복·근무일·시간 순서는 상신에서 검사한다.

휴가 원장은 상신 RESERVE, 최종 승인 USE+RELEASE, 반려·회수 RELEASE만 추가한다. 기존 연차 정책 조회와 신규 사원의 직급별 초기 부여는 저장 위치만 원장으로 바꿔 유지한다. M3 정기 부여 배치는 추가하지 않았다. 기존 사용자 응답의 연차 숫자는 원장 합계의 읽기 전용 투영이다. 기존 캘린더·대시보드의 조회는 문서 상태를 읽는 호환 매핑으로 유지한다.

## 부작용·남은 위험
- 기존 정책은 직급별 초기 부여다. 법정 부여 규칙이나 정기 배치는 M3에서 결정한다.
- 2차 사용자 확정: 연도를 넘는 휴가는 상신에서 422 LEAVE_CROSS_YEAR로 거절하고 미리 계산에서는 같은 메시지를 error로 반환한다. 시작일 연도 귀속이라는 1차 임시 판단은 폐기했다.
- 기존 조회 호환용 응답 필드는 여러 연도의 합계다. 새 연차 API는 명세대로 연도별 합계를 제공한다.
- 구 연차·특근 쓰기 API는 2차에서 제거했다. GET /leave/policy 및 대시보드·캘린더 조회는 호환 유지한다.

## 결과
CoreApiIntegrationTest의 9개가 새 계약과 MariaDB에서 전부 통과했다. 비활성 특근 테스트를 같은 이름으로 복구했으며 건너뜀은 없다. 로그인·사원 목록·연차·특근 승인·캘린더·근태·중복 기간·반차·회수 회귀를 유지했다. M2에서는 반차 기간을 자동 보정하지 않고 명세대로 같은 날인지 검사한다. 최종 1차 통합 실행 결과는 M2-4 문서에 기록한다.
