# M2-4 — 문서 상태 전이·동시 승인·알림 원자성

## 증상
기존 연차 승인은 PENDING을 읽고 조건 없이 저장하여 같은 건을 두 요청이 모두 승인할 수 있었다.

## 재현 방법
M2LegacyApprovalRaceTest는 실제 MariaDB 10.11에서 V2까지 적용한 뒤 기존 “상태 읽기 → 사용자 잔여 읽기 → 무조건 갱신” 구조를 실행한다. 두 트랜잭션이 모두 읽은 뒤 쓰도록 장벽을 두고 10회 반복했다. 이는 경쟁 조건의 통제된 재현이며 자연 발생 확률을 뜻하지 않는다.

## 원인
상태 전이 조건·버전·사용자별 잔여 잠금이 없어 두 요청 모두 이전 상태를 근거로 성공 처리된다.

## 검토했지만 버린 방법과 이유
JVM synchronized는 다른 프로세스에서의 경쟁을 막지 못하고, Redis 잠금은 이번 범위 밖이다. 결재와 연차를 별도 트랜잭션으로 처리하면 일부만 성공할 수 있어 사용하지 않는다.

## 선택한 방법
사용자 → 문서번호 발급 행(상신만) → 문서 행 순서로 잠근다. 승인 줄은 WHERE status='PENDING'인 조건부 갱신의 영향 행이 1이어야 하고, 문서 갱신은 version 조건을 추가한다. 사용자 잠금을 기다린 뒤 최신 원장을 읽도록 READ_COMMITTED를 사용한다. 권한 확인은 쓰기보다 먼저 하며 실패하면 전체 트랜잭션을 롤백한다.

알림은 명세 6장대로 결재·원장과 같은 트랜잭션이다. 사용자 확인과 양방향 롤백 근거는 [M2-7](M2-7-notification-transaction.md)에 기록했다.

## 부작용·남은 위험
사용자별 상신·결재가 직렬화되고 같은 양식·연도의 번호 발급도 직렬화된다. 현 규모의 일관성을 우선하며 별도 번호 발급 트랜잭션은 만들지 않았다. 구 API 제거와 결재함 대량 조회 검증은 2차 작업이다. 기존 대시보드의 전체 연차 목록 등 새 API 밖의 권한 경로는 범위 밖 문제로 별도 보고하며 임의 수정하지 않는다.

## 결과
- 수정 전: 10회 중 10회 중복 성공 (M2_LEGACY_APPROVAL_RACE).
- 수정 후: 실제 HTTP 요청 두 개를 동시에 시작한 10회에서 매번 200 하나·409 DOCUMENT_STATE_CONFLICT 하나. 중복 성공 0/10, 실패 요청의 추가 알림 0/10, 문서당 USE 1회.
- 수정 전의 읽기 뒤 장벽은 경쟁을 확실히 만들기 위한 장치다. 수정 후에는 사용자 잠금 때문에 두 요청이 동시에 해당 읽기 지점에 도달할 수 없으므로 요청 시작 장벽을 사용한다. 입력·두 요청·10회 반복·중복 성공 판정은 동일하다.
- 승인 대 회수는 하나만 성공, 잔여 2일의 동시 2일 신청도 하나만 성공한다. 서로 다른 기안자 8명의 동시 상신 번호는 중복이 없다.
- 알림 INSERT 뒤 강제 예외에서 문서·줄·원장·이력·알림이 원래 상태로 돌아간다.

Java 17.0.16 + Docker + UTC JVM에서 다음 명령으로 1차 관련 22개를 함께 실행했다. 성공 22, 실패 0, 오류 0, 건너뜀 0, BUILD SUCCESS.

```sh
./mvnw -Duser.timezone=UTC -Dtest=M2DocumentIntegrationTest,CoreApiIntegrationTest,M2DataMigrationTest,M2LegacyApprovalRaceTest test
```

각각 11/9/1/1개다. 이 결과는 전체 테스트 결과가 아닌 1차 관련 통합 검증이다. 전체 테스트 및 구 API 제거 회귀·대량 결재함 검증은 2차 작업에서 실행한다. frontend, backend/md, V1·V2, .claude/, 로컬 개발 DB는 변경하지 않았다.
