# M3-2 — 서버 시각 출퇴근·판정과 KI-04

## 증상
사용자가 과거 날짜와 08:50을 보내면 실제 서버 시각과 무관하게 정상 출근을 만들고 직접 PUT으로 고칠 수 있었다.

## 재현 방법
운영 코드 수정 전 develop 5f85a6f에서 M3SecurityTest로 실제 /attendance/check-in에 두 주 전 날짜+08:50을 10회 전송했다. 10/10이 해당 날짜·시각·NORMAL로 저장됐다. 최초 실행 로그 표식: M3_KI04_BEFORE attempts=10 forged=10. V3 구조 비교용 M3LegacyAttendanceTest도 남겼다.

## 원인
기존 서비스는 요청의 workDate/clockInTime을 검증 후 그대로 저장했다. 기존 동시 출근은 잠금 없는 존재 확인 후 INSERT라 유니크 충돌이 일반 예외로 새어 나갔다.

## 검토했지만 버린 방법과 이유
본문 시각을 허용 범위 안에서만 받는 방식도 사용자가 기록을 선택하게 하므로 제외했다. JVM synchronized/Redis 잠금은 DB 행 잠금보다 범위가 좁거나 새 운영 요소가 필요해 제외했다.

## 선택한 방법
clock-in/clock-out은 본문을 받지 않고 Clock(Asia/Seoul)의 현재 시각을 기록한다. 사용자 행→근태 행 잠금 순서로 존재 확인·판정을 수행한다. 중복 출근은 409 ALREADY_CLOCKED_IN, 퇴근은 마지막 서버 시각으로 갱신한다. 근무시간·유예·출처·부서를 스냅샷으로 저장하고 지각은 분 단위 경계 포함, 조퇴는 정확한 기준 시각으로 비교한다. 종일 휴가는 거절하고 휴일 출근은 NONE 판정이다. 다음 날 퇴근은 전날 열린 기록에만 연결하고 같은 다음 날의 재퇴근도 갱신한다.

## 부작용·남은 위험
V4가 옛 시각 컬럼을 제거하고 KI-04를 1차에 닫아야 하므로, 구 쓰기/summary 라우트 제거는 2차 예정에서 1차로 앞당겼다. 외부 API 최종 계약은 명세와 같다. 남은 사용하지 않는 구 DTO 정리는 2차에서 한다. 출근 뒤 승인된 반차는 명세대로 다음 날 배치가 재판정한다. 야간 교대 제도 전체는 범위 밖이다.

## 결과
새 API에 같은 조작 본문을 10회 보내도 조작 성공은 0/10이고 모두 서버 시각으로 저장된다. 실제 기존 API 재현과 새 API는 같은 입력/10회이나 URL은 명세 변경대로 다르다. V3 읽기 후 INSERT 비교 실험은 두 읽기를 장벽으로 맞춰 10/10 유니크 예외를 재현했다(행 중복은 기존 유니크가 방지). 새 HTTP 동시 요청 10회는 매회 200 하나·409 하나, 기록 1행. 분 경계·반차·스냅샷·반복 퇴근·UTC 자정·권한 거절 쓰기 없음 및 내 월간 모든 날짜를 M3AttendanceTest로 검증했다.
