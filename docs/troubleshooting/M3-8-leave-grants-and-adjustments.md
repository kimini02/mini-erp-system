# M3-8 — 연차 자동 부여와 관리

## 증상
신규 사원이 입사 당일 직급별 14일을 받는 기존 정책이 M3 입사일 기준 월/연 부여와 충돌한다. 누락 보충·수동 조정의 중복 및 잔액 경합도 보호해야 한다.

## 재현 방법
수정 전 M3GrantRegistrationTest가 입사 당일 기대 0일 대신 14일로 1/1 실패했다. M3LeaveAdjustmentConcurrencyTest는 먼저 잠금 없는 잔액 읽기→검사→ADJUST 추가 모델을 2스레드×10회 실행한 뒤 실제 새 API에 같은 -6일 조정을 2개씩 보낸다.

## 원인
기존 등록 서비스는 직급 이름으로 즉시 부여했다. 잔액만 읽고 각자 쓰면 같은 10일을 두 요청이 동시에 사용한다.

## 검토했지만 버린 방법과 이유
기존 원장을 삭제하거나 v1 부여분을 자동 상계하는 방법은 명세에 정산 규칙이 없어 제외했다. 분산 잠금·새 라이브러리는 쓰지 않는다. 일별 증분만 계산하면 놓친 실행을 복원하지 못한다.

## 선택한 방법
새 등록의 직급별 부여를 중단하고 명세 4.1의 월 1~11개월·1주년 비례·1월 1일 부여를 사용한다. 대상일까지의 모든 키를 계산하고 사용자 ID 순서의 행 잠금+grant_key 유니크로 누락 보충과 중복 방지를 보장한다. 연도는 실행 연도가 아닌 부여 예정일 연도다. 00:30 스케줄과 수동 실행은 같은 서비스다. 배치 기록기를 global.batch로 옮겨 결근·연차가 공통 사용한다. processed_count는 새 원장 건수, skipped_count는 입사일 없는 사원 수이며 message에 ID를 남긴다. 조정은 메뉴 C·대상 범위 확인 후 상신과 같은 사용자 행 잠금/READ_COMMITTED로 합계를 읽고 ±0.5일·비영·음수 잔액 금지·created_by를 적용한다.

## 부작용·남은 위험
회사 규정으로 가정한 명세 계산이며 일반 법정 산정기는 아니다. 결정 필요: v1 이관/옛 신규 등록 GRANT와 소급 자동 부여 키 사이의 정산 기준. 명세대로 기존 원장은 보존하고 모든 예정 키를 채우므로 정책 전환 전 기존 부여분과 겹치는지 확인해야 한다. 입사일 변경이나 재입사 시 기존 부여 키를 재계산/취소하는 규칙도 없다. 원장은 임의 보정하지 않는다. 배치 한 번은 전체 대상 사용자에 대한 단일 트랜잭션으로 다수 사원이면 잠금 대기가 늘 수 있다.

## 결과
신규 등록 14일→0일. 월말 1/31→2/28, 월 부여 11건=11일, 7/1의 1주년 8일, 1/1의 1주년 15일(중복 Y 없음), 근속 3년 16일·21년 25일을 실제 원장으로 검증했다. 동시 배치 10회 중 중복 0회. 잠금 없는 비교 모델은 음수 잔액 10/10, 실제 조정 API는 0/10이며 매회 200·422. 상신과 조정 경합에서도 한쪽만 성공하고 잔액 4일. 비교 모델은 기존 운영 조정 API가 있었던 것으로 주장하지 않는다. M3LeaveGrantTest 5개, 등록 1개, 경합 1개 및 최종 전체 결과는 M3-10 참조.
