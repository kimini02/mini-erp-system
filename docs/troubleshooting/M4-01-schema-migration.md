# M4-01 — 프로젝트 키·보드 데이터 이관

## 증상
v1에는 업무 번호, 순서, 버전, 변경 이력이 없어 새 보드 계약을 채울 수 없다. 새 필수 컬럼만 추가하면 기존 행이 유효하지 않게 된다.

## 재현 조건
`M4DataMigrationTest.v6KeepsLegacyDataAndNumbersEachProjectAndColumn`: MariaDB 10.11 Testcontainers에 V1~V5를 적용하고 프로젝트 2개, 업무 5개를 넣은 뒤 V6을 실행한다. 개발 DB는 사용하지 않았다.

## 원인
프로젝트·업무는 v1 JPA 구조를 유지하고 있었고, 팀장과 프로젝트 멤버도 별도였다. 기존 알림은 `document_id NOT NULL`이라 결재 문서가 없는 업무 배정 알림을 저장할 수 없었다.

## 검토했지만 버린 방법
- V1~V5 수정 또는 Hibernate 자동 스키마 변경: 배포 이력과 명세 위반.
- 기존 업무 번호를 전역 id로 표시: 프로젝트별 연속 번호 계약과 다름.
- 업무 알림에 가짜 결재 문서 지정: 의미와 참조 관계가 잘못됨.

## 선택과 이유
V6만 추가했다. 프로젝트 키는 `P{id}`, 업무 번호는 프로젝트별 id 순, position은 프로젝트·상태별 id 순의 1024배다. `last_task_seq`도 이관한 최대 번호로 설정한다. 누락된 팀장 멤버십을 추가하고 이관 건수를 로그에 남긴다. 기존 업무의 작성자는 추측하지 않고 NULL, version은 0이다. 이력·마감 알림 테이블과 조회 목적 주석을 가진 인덱스를 추가했다.

업무 알림에 한해 결재 문서가 없으므로 V6에서 `notifications.document_id`를 NULL 허용으로 바꿨다. 기존 외래키와 결재 알림은 유지한다. 마감 알림 배치는 2차 범위다.

## 전후 수치 / 결과
- 프로젝트 2개: 키 없음 → P1/P2, last_task_seq 3/2.
- 업무 5개: task_no 없음 → 1,2,3,1,2; position → 1024,1024,2048,1024,1024.
- 누락된 팀장 멤버 2건 보완. 기존 제목·내용·날짜·상태·소속 프로젝트 값 변화 0건.
- 로그: `M4: migrated_projects=2`, `M4: migrated_tasks=5`, `M4: migrated_leader_members=2`.
- 재실행 마이그레이션 0건, Flyway validate 통과.
- `MariaDbMigrationTest`까지 포함한 초기 확인: 4/4 성공, 실패·건너뜀 0.

## 남은 위험
MariaDB DDL은 일부 실패 시 전체 롤백되지 않는다. 운영 적용 전 백업·복구 절차가 필요하다. 명세의 P{id} 규칙은 id가 10억 이상이면 VARCHAR(10)을 넘는다. 이번에는 명세대로 구현했으며 이런 기존 id의 별도 매핑은 결정 필요다. 새 테이블은 마감 배치 구현을 의미하지 않는다.
