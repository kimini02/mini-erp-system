# M4-02 — 수정 전 구조 재현 기록

## 증상
서로 다른 업무를 동시에 완료하면 업무는 모두 DONE인데 프로젝트는 PROGRESS로 남는다. 목록 전체 로딩은 업무 수만큼 행을 만들고, 순서를 모두 다시 쓰면 이동 한 번에 카드 수만큼 UPDATE한다.

## 재현 조건
`M4LegacyExperimentTest`, Java 17, MariaDB 10.11 Testcontainers, READ COMMITTED. 2026-10-27 수정 후 상태·순서 서비스를 구현하기 **전** 먼저 실행했다. `/private/tmp/m4-before.log`는 당시 로컬 실행 로그이며 재현 가능한 원본은 테스트 코드다.

- 쓰기 왜곡: 업무 2개를 별도 실제 스레드·트랜잭션으로 완료. 각 업무 UPDATE 후 barrier, 상태 목록 조회 후 barrier, 프로젝트 UPDATE/commit. 이를 10회 반복.
- 상태 계산 비용: 업무 1,000개, 업무 UPDATE → 전체 목록 SELECT → 프로젝트 UPDATE. 예열 3회, 측정 9회, 트랜잭션 시작~커밋 중앙값.
- 순서: 카드 100개, 마지막 카드를 맨 앞으로 이동하며 전체 100행 UPDATE. 별도 실험으로 두 카드가 같은 간격을 읽은 후 barrier에서 만나 각각 중간값으로 이동. 20회 반복, 매회 같은 초기 간격 복원.

## 원인
READ COMMITTED에서는 각 트랜잭션이 상대의 커밋 전 업무 변경을 볼 수 없다. 두 목록 모두 미완료 업무를 포함하고, 나중의 프로젝트 UPDATE도 그 오래된 계산을 저장한다. 순서도 같은 간격을 동시에 읽으면 같은 중간값을 고른다.

## 검토했지만 버린 방법
- 우연히 경합이 생길 때까지 반복: OS 스케줄링에 따라 재현이 불안정하다.
- 프로젝트 저장 직전만 잠금: 상태 계산 시점의 오래된 읽기를 막지 못한다.
- 재현 횟수를 운영 장애 확률로 설명: 강제로 취약한 순서를 만든 실험이라 통계적으로 잘못된 해석이다.

## 선택과 이유
기존 `Project.updateStatusByTasks`의 핵심인 **잠금 없는 전체 목록 읽기·계산·쓰기**를 JDBC 비교 구현으로 분리했다. 엔티티 전체 그래프와 지연 로딩 시간까지 재현한 것은 아니다. 기존 서비스의 READY 전이 예외와 분리해 쓰기 왜곡만 검증한다. v1에는 카드 순서 기능이 없으므로 순서 실험은 전체 재번호·잠금 없는 중간값 방식의 비교 구현이다.

## 전후 수치 / 결과
최초 수정 전 실행 3/3 통과는 **결함 재현 조건이 충족됐다는 뜻**이다.

| 최초 수정 전 관측 | 결과 |
|---|---:|
| 쓰기 왜곡 | 10/10 |
| 상태 계산 반환 행 | 1,000 |
| 상태 계산 SQL | 3 (SELECT 1 + UPDATE 2) |
| 상태 계산 중앙값 | 9.101 ms |
| 전체 재번호 UPDATE 행 | 100 |
| 동시 이동 20회 위치 중복 합계 | 20 (매회 1개) |

최종 비교는 같은 실행에서 전후를 번갈아 측정한 [상태 계산 비용](M4-05-status-cost.md)을 사용한다. 단독 최초 실행 9.101ms와 다른 실행의 시간을 직접 비교하지 않는다. 수정 후 정합성·순서는 [쓰기 왜곡](M4-04-write-skew.md), [카드 순서](M4-06-card-order.md)에 기록한다.

## 남은 위험
이 수치는 통제한 경합 조건의 재현성이다. 운영에서 매번 오류가 난다는 뜻이 아니다. 기기·Docker 부하에 따라 지연 시간은 달라지므로 속도 배수를 테스트의 성공 조건으로 삼지 않는다.
