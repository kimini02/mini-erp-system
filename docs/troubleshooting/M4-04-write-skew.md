# M4-04 — 마지막 두 업무 완료의 쓰기 왜곡

## 증상
두 업무가 모두 DONE인데 프로젝트의 저장 상태는 PROGRESS다.

## 재현 조건
수정 전 `M4LegacyExperimentTest.unlockedWholeListRecalculationReproducesWriteSkewTenTimes`를 먼저 실행했다. 실제 MariaDB 10.11, READ COMMITTED, 2개 스레드·별도 트랜잭션, 프로젝트별 남은 업무 2개다. 각자 업무를 완료한 뒤 두 상태 목록을 상대 commit 전에 읽도록 barrier로 제어한다. 10회 반복했다.

수정 후 `M4BoardConcurrencyTest.projectLockPreventsWriteSkewInTenConcurrentCompletions`는 같은 두 미완료 업무를 각 담당자의 JWT로 동시에 이동한다. barrier는 HTTP 호출 직전에 둔다. 잠금 뒤 barrier를 두면 두 번째 트랜잭션이 잠금 대기 중이므로 첫 번째도 barrier를 기다리는 인위적 교착을 만들기 때문이다.

## 원인
상대가 커밋하지 않은 업무 상태는 보이지 않는다. 각각의 목록에는 미완료 업무가 하나씩 남아 있어 둘 다 PROGRESS를 계산한다. 프로젝트 저장 시점에만 잠그거나 마지막 저장이 이겨도 잘못 계산한 값은 그대로다.

## 검토했지만 버린 방법
- JVM synchronized: 서버가 여러 프로세스면 보호되지 않는다.
- Redis/분산 잠금 라이브러리: 사용 제약 위반이며 동일 MariaDB 안의 상태라 불필요하다.
- 프로젝트 UPDATE 직전에만 잠금: 계산에 사용한 읽기를 직렬화하지 못한다.
- 모든 업무를 FOR UPDATE: 잠금 대상이 늘고 순서·번호까지 같은 경계로 보호하기 어렵다.

## 선택과 이유
모든 업무 쓰기는 프로젝트 행을 먼저 FOR UPDATE한다. 잠금을 얻은 뒤 업무·version을 읽고 변경하며, 같은 트랜잭션 안의 GROUP BY로 프로젝트 상태를 다시 쓴다. 두 번째 요청은 첫 번째 commit 후 전체 업무의 최신 상태를 읽는다. 업무 id로 프로젝트 id를 찾는 선행 SELECT는 잠금 없는 식별 조회이고, 실제 상태·권한 검사는 프로젝트 잠금 후 다시 한다.

기존 쓰기 경로도 사용자 승인에 따라 새 서비스에 연결했다. 업무 추가·일반 수정·이동·담당자 변경 모두 같은 잠금과 상태 계산을 쓴다. 여러 프로젝트 멤버십을 바꾸는 기존 경로는 프로젝트 id 오름차순으로 잠근다.

## 전후 수치 / 결과
| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 두 업무 모두 완료인 프로젝트의 상태 불일치 | 10/10 | 0/10 |
| 각 시행의 완료 업무 | 2 | 2 |

기본·UTC 전체 실행에서도 같은 결과다. READY(0개/모두 TODO), DONE(모두 완료), PROGRESS(그 외), DONE에서 다시 TODO로 이동하는 전이도 검증했다.

## 남은 위험
같은 프로젝트의 쓰기는 직렬화되므로 아주 활발한 대형 프로젝트는 잠금 대기가 늘 수 있다. 1차는 문서의 수백 카드 가정을 따른다. 잠금 시간 제한·별도 재시도·전역 분산 처리는 추가하지 않았다. 구 JPA 서비스의 쓰기 메서드는 HTTP에서 호출되지 않지만 2차 삭제 전 내부 코드에 남는다. 새로운 호출자를 추가하면 다시 우회할 수 있으므로 2차에서 제거해야 한다.

## 2차 리뷰 보완 — 결정적 대기 증거
**10/10은 barrier로 최악의 순서를 강제한 재현율이며 운영 발생 확률이 아니다.** 시작 barrier만으로는 수정 후 커밋 전 경합을 보장하지 못해, 첫 업무 UPDATE 뒤 멈춘 동안 두 번째 이동의 실제 MariaDB 잠금 대기를 관측하는 테스트를 추가했다. 완료 순서는 HTTP 반환 스케줄이 아닌 DB commit 가시성으로 검증한다. [M4-09](M4-09-deterministic-lock-wait.md)의 대기 행·시간·이벤트 순서를 참고한다.
