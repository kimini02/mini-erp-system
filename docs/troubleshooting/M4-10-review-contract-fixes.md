# M4-10 — 이력·알림 제목·검색·퇴사자 멤버 보완

## 증상
MOVED 이력에 내부 position 숫자가 노출되고, 배정 이력의 대상 id만으로는 빠진 멤버 이름을 표시할 수 없다. 알림 제목에 문장 접두어가 들어가고, 검색의 %/_가 와일드카드로 작동하며, 기존 퇴사자 멤버가 있으면 멤버 저장 전체가 막힌다.

## 재현 조건
`M4ReviewRegressionTest`의 5개 테스트를 수정 전에 실행해 **5개 실패, 오류·건너뜀 0**을 확인했다. 이동 이력 응답, 멤버 제거 뒤 ASSIGNED/UNASSIGNED 이름, 배정 알림 제목, 리터럴 검색, 기존 퇴사자 유지·제거·재추가를 실제 API/MariaDB로 검증한다.

## 원인
이력 저장값을 응답에 그대로 내보내고, 알림 저장 단계에서 문장을 붙였다. LIKE 패턴을 직접 연결했고, 멤버 전체에 신규 등록의 ACTIVE 검사를 적용했다.

## 검토했지만 버린 방법
- 화면에서 position이나 과거 대상 id를 해석: 사용자 의미가 없거나 이미 멤버가 아니라 이름을 얻을 수 없다.
- 사용자 이름을 매 이력마다 별도 조회: N+1이 된다.
- 퇴사자 검사를 전부 제거: 새 퇴사자 추가도 허용하게 된다.

## 선택과 이유
MOVED는 응답에서 from/to를 생략하되 저장된 숫자는 유지한다. ASSIGNED/UNASSIGNED는 이력 조회의 users LEFT JOIN으로 target:{id,name}을 함께 반환한다. 멤버십 삭제와 무관하며 과거 이름 스냅샷이 아닌 현재 사용자 이름이다.

TASK_ASSIGNED 제목은 `프로젝트키-업무번호 제목`만 저장한다. 링크는 확정된 `/projects/{id}/board?taskId=`를 유지한다. 검색은 ! 자체부터 이스케이프하고 %/_를 이스케이프한다. 재직 검사는 새 멤버에만 하며 기존 퇴사자는 유지·제거할 수 있다. 미완료 담당자 제거 409 검사는 유지한다.

확정된 권한 결정도 등록에 적용했다: PROJECT V를 먼저 확인한 다음 C를 검사한다. C만 있고 V가 없는 등록은 403이며 DB 변화가 없다. PATCH task의 version 검사 없음, 이동 응답/409 wrapper는 사용자 결정대로 유지했다.

## 전후 수치 / 결과
- 회귀 5개: 5개 실패 → 모두 성공.
- 새 V+C 결정 검증 포함 6/6 성공.
- 결정적 잠금 테스트와 합산 8/8 성공.
- 이력 조회는 대상 이름을 조인하므로 이력 수에 따른 추가 쿼리 없음.

## 남은 위험
target.name은 현재 이름이다. 향후 사원 이름 변경 시 과거 이력 표시도 바뀐다. 사용자 삭제는 현재 사원 퇴사와 다르며 삭제 정책은 이번 범위가 아니다. 기존 저장된 접두어 알림은 일괄 변경하지 않았다.
