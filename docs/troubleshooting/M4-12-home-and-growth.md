# M4-12 — 홈 통합 조회와 실제 스캔 비용

## 증상
홈 데이터가 여러 요청으로 나뉘고 옛 dashboard/projects는 프로젝트마다 COUNT를 두 번 수행했다. 쿼리 수를 고정해도 옵티마이저가 전체 휴가를 먼저 읽으면 데이터 증가에 따라 비용이 커진다.

## 재현 조건
변경 전 실제 `GET /dashboard/projects`에서 프로젝트 5개에 업무 COUNT 10번, HTTP SQL 총 13번을 먼저 확인했다(`M4QueryGrowthTest`, 제거 전 실행). 삭제 뒤에는 같은 1+2N 구조의 비교 구현 11쿼리를 남겼다. 13에는 인증 조회 등이 포함되며, 담당 팀장 분포에 따라 지연 로딩 횟수는 달라질 수 있다.

화면 소스의 정적 호출 조사: AdminDashboard의 `/tasks` 1개와 AppLayout → approvalStore.refresh의 결재 건수·대기 목록·알림 건수 3개로 초기 데이터 요청 4개(결재함 권한 보유 기준). UserDashboard 자체는 가짜 데이터이며 공유 레이아웃 3개가 있다. 알림 메뉴를 열 때 목록 조회 1개가 추가된다. 인증 초기화 `/me`·권한 조회, StrictMode 재실행·포커스 갱신은 제외했다. 기존 화면이 새 홈의 모든 위젯을 실제로 조회했다는 뜻은 아니다. 프론트 수정/브라우저 실측은 하지 않았으므로 **프론트 요청이 이미 4→1로 바뀌었다고 주장하지 않는다**. 새 홈 데이터 계약은 GET /home 한 번이다.

`M4HomeGrowthTest`: MariaDB 10.11 Testcontainers, 전체 업무 1,000/10,000/100,000, 결재 문서·휴가·알림 각각 100/1,000/10,000. 내 업무도 20/200/2,000으로 증가하며 내 부서 휴가 문서는 10/100/1,000이다. 예열 3회, 측정 9회 중앙값. 명세의 수백 개 보드 가정을 넘는 2,000개 프로젝트도 측정용으로 포함했다. ANALYZE FORMAT=JSON으로 운영 SQL의 키·r_loops·r_rows를 출력한다.

## 원인
- 옛 화면/API의 응답이 분산돼 있고 구 프로젝트 요약은 1+2N이다.
- 최초 홈 구현의 자유로운 JOIN 순서에서는 100배 데이터에서 휴가 전체 10,000행을 읽었다. 내 부서부터 시작하는 계획이 항상 선택되지 않는다.
- 공용 프로젝트 요약을 홈의 최다 업무 프로젝트 선택에 그대로 쓰면 같은 후보 선택을 CTE 참조별로 반복한다.

## 검토했지만 버린 방법과 이유
- 권한 무시한 전체 데이터 로딩 후 Java 필터: 데이터 범위 규칙 위반.
- 요청/권한 결과의 전역 캐시: 권한 회수 반영과 무효화 비용이 생긴다.
- 새 인덱스·V7: 실제 계획에서 기존 사용자 부서, 담당자, 문서 작성자 및 업무 프로젝트 인덱스로 범위를 줄일 수 있었다. 근거 없는 인덱스를 추가하지 않았다.
- 위젯마다 기존 목록 API 전체 호출: 중복 COUNT·권한·조직 조회로 SQL 목표를 넘는다.

## 선택과 이유
홈 전용 읽기 서비스에서 위젯마다 SQL을 고정한다. 근태는 기존 AttendanceService의 응답 판정 코드를 공유하고 한 번의 joined snapshot을 사용한다. 결재 대기 3건/내 기안 3건, 내 업무 5건, 알림 5건을 SQL에서 제한한다. 팀 항목은 내 부서만, 업무는 PROJECT 보기 범위도 SQL에서 적용한다. 사유는 반환하지 않는다.

팀 조회는 부서 사원 → 담당 관계/문서 → 업무/휴가 순서를 STRAIGHT_JOIN으로 고정한다. 내 최다 업무 프로젝트는 한 번 선택한 파생 결과에서 그 프로젝트의 업무만 집계한다. 해당 사용자의 업무·알림 증가 비용은 남으며 O(1) 응답 비용을 주장하지 않는다.

권한 해석(사용자 추가 결정): today=MY_ATTENDANCE V, approvals=APPROVAL_INBOX V, myTasks=PROJECT V. teamWeek의 휴가는 MY_ATTENDANCE V, 업무는 PROJECT V+보기 범위이고 둘 다 없으면 null. 개인 leave/notifications는 기존 API처럼 로그인만 요구한다. 사용자가 항목별 메뉴 권한 적용을 확정했다. myTasks.items는 선택된 프로젝트에 국한하지 않고 내 보기 범위의 미완료 전체 중 마감일순 5건이다.

## 전후 수치
동일 실행의 paired team SQL 비교(2026-10-27). 시간은 참고치다.

| 배율 | 홈 HTTP SQL | 홈 ms | 팀 휴가 읽기 전→후 | 팀 업무 읽기 전→후 | 팀 SQL ms 전→후 |
|---:|---:|---:|---:|---:|---:|
| 1 | 14 | 23.342 | 10→10 | 20→20 | 0.818→0.817 |
| 10 | 14 | 23.403 | 100→100 | 200→200 | 2.590→1.812 |
| 100 | 14 | 60.611 | 10,000→1,000 | 4,000→2,000 | 16.956→13.581 |

100배 ANALYZE 주요 항목(실제 접근 행 수=r_loops×r_rows):

| 쿼리·테이블 | 선택 키 | r_loops | r_rows | 합계 |
|---|---|---:|---:|---:|
| 내 업무 a | idx_task_assignments_user | 1 | 2,000 | 2,000 |
| 내 업무 t | PRIMARY | 2,000 | 1 | 2,000 |
| 내 프로젝트 후보 t | PRIMARY | 2,000 | 1 | 2,000 |
| 내 프로젝트 집계 t | uk_tasks_project_no | 1 | 2,000 | 2,000 |
| 팀 휴가 person | idx_users_department_status | 1 | 2 | 2 |
| 팀 휴가 d | idx_documents_drafter_status | 2 | 500 | 1,000 |
| 팀 휴가 l | uk_leave_requests_document | 1,000 | 1 | 1,000 |
| 팀 업무 a | idx_task_assignments_user | 2 | 1,000 | 2,000 |
| 팀 업무 t | PRIMARY | 2,000 | 1 | 2,000 |

최초 홈 구현을 수정하기 전 실행에서도 휴가 전체 10,000행을 확인했다. 그 SQL을 `LegacyHomeQueries`에 보존해 후속 실행에서 같은 결과와 계획을 비교한다. 내 프로젝트 선택·집계의 task 접근은 최초 8,000행에서 4,000행으로 줄었다(후보 3회→1회). 내 업무 자체는 20/200/2,000행으로 대상 업무 수에 비례한다. 프로젝트 목록·보드 요약 10배·100배 계획은 M4-11에 별도 기록했다.

## 결과
M4HomeTest 4개 + M4HomeGrowthTest 1개 통과. 근태 응답 일치(출근·공휴일·승인 반차), 누락 권한 위젯 null, 타 부서/권한 밖 프로젝트 제외, 결재·알림 제한과 건수, 한국 월요일 00:30 및 시간대 없는 시각을 확인했다. 14쿼리는 인증·권한 포함 SELF 기준이고 DEPT_TREE는 하위 부서 조회 1회가 더해진다.

## 부작용·남은 위험
READ COMMITTED의 여러 SELECT라 동시에 상태가 바뀌면 위젯 사이에 아주 짧은 시점 차이가 있을 수 있다. 팀 주간 응답은 목록 크기 제한이 없어 내 부서의 업무 자체가 많으면 반환량이 늘어난다. 강제 JOIN 순서는 현재 측정 분포에 맞춘 것이며 부서/업무 분포 변화 시 재측정해야 한다. 기존 화면·레이아웃의 별도 요청 제거는 프론트 작업에서 수행한다.
