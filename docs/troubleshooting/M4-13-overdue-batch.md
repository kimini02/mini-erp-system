# M4-13 — 마감 업무 알림의 반복 실행과 롤백

## 증상
마감 알림은 재시작·중복 스케줄 실행 때 같은 담당자에게 반복 발송될 수 있다. M4 이전에는 이 배치 자체가 없어 이전 운영 발생률·성능 수치는 없다.

## 재현 조건
`M4OverdueTest`, MariaDB 10.11 Testcontainers. 어제 마감인 DOING 업무, 담당자, 주입 Clock. 동일 배치 2회, 마감일 변경 후 재실행, DONE 전환 후 재실행, 실제 스레드 2개 동시 실행, 알림 저장 예외 주입을 검증한다.

## 원인
알림 INSERT만 반복하면 실행 횟수만큼 저장된다. DB 커밋 뒤에 중복 표시를 하거나 표시와 알림을 서로 다른 트랜잭션으로 처리하면 실패 시 재시도가 유실·중복될 수 있다.

## 검토했지만 버린 방법과 이유
- Redis·분산 잠금 라이브러리: 금지 조건이며 V6의 유니크 제약과 프로젝트 잠금으로 충분하다.
- AFTER_COMMIT 알림: 앱 안 알림은 결재 때와 마찬가지로 업무 DB 상태다. 실패 시 중복 방지 표시도 취소되어야 한다.
- 실행 날짜를 중복 키로 사용: 매일 반복 알림이 생긴다. 명세는 업무·담당자·마감일당 한 번이다.

## 선택과 이유
`TaskOverdueWork`의 READ COMMITTED 트랜잭션에서 프로젝트 id 순으로 프로젝트 행을 먼저 잠그고, 최신 마감·상태·담당자를 다시 조회한다. `task_due_alerts(task_id,user_id,due_date)` 유니크 키를 최종 중복 방지 장치로 사용하며 알림·OVERDUE_NOTIFIED 이력도 같은 트랜잭션에 저장한다. 제목은 `프로젝트키-번호 제목`, 링크는 `/projects/{id}/board?taskId=`다. 이력은 실제 알림을 받은 담당자마다 한 건이다.

스케줄은 한국 시각 09:00, `app.batches.enabled=false`면 비활성이다. 수동 HTTP API는 명세에 없어 추가하지 않았다. 스케줄과 테스트 모두 `TaskOverdueService.runToday()`를 사용한다. 성공·실패 실행 기록은 기존 M3 BatchRunRecorder로 남긴다.

## 전후 수치·결과
신규 기능이므로 존재하지 않았던 과거 배치와의 속도 비교는 하지 않았다. 반복 실행 전후의 누적 결과다.

| 실험 | 누적 알림 | 중복 방지 행 | 결과 |
|---|---:|---:|---|
| 최초 실행 → 같은 조건 재실행 | 1→1 | 1→1 | 추가 0 |
| 마감일 변경 후 실행 | 1→2 | 1→2 | 새 마감일 한 번 |
| DONE 전환 후 마감일 변경·실행 | 2→2 | 2→2 | 추가 0 |
| 2개 스레드 동시 실행 | 1 | 1 | 중복 0 |
| 알림 저장 실패 | 0 | 0 | 이력도 0, FAILED 기록 1 |
| 실패 후 재시도 | 1 | 1 | 정상 복구 |

세 테스트 모두 통과. 정상 순차 실험의 batch_runs SUCCESS 기록은 4개다. 이 측정은 기능 정합성 증거이고 운영 장애 발생 확률 추정이 아니다.

## 부작용·남은 위험
한 실행에서 프로젝트를 순서대로 잠그므로 대량 미완료 업무가 있으면 보드 쓰기가 기다릴 수 있다. 중복 표시는 남기므로 저장 공간이 증가한다. 업무 트랜잭션 커밋 직후 프로세스가 죽으면 실행 기록이 없을 수 있지만 재시도 알림은 유니크 키로 중복되지 않는다. 외부 메일은 발송하지 않는다. 명세대로 퇴사 여부 대신 현재 업무 담당 관계를 기준으로 한다.
