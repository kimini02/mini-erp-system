# M5-13 한국 월 경계 테스트의 판별력

## 증상
기존 15일 00:30 테스트는 한국/UTC 날짜는 달라도 월은 같아서 UTC 월로 잘못 세는 구현을 검출하지 못한다.

## 재현 방법
고정 Clock 기준 월의 1일 00:30(한국)을 설정한다. 전달 마지막 이틀의 결근 2건, 이번 달 1일 결근 1건을 만든다. Clock의 UTC 날짜가 전달 말일임을 먼저 단언한 뒤 /attendance/today와 /home.today의 monthAbsentCount가 각각 1인지 assertAll로 확인한다.

## 원인
전달과 이번 달의 표본 수가 같으면 잘못된 월을 조회해도 같은 값이 나와 판별할 수 없다.

## 검토했지만 버린 방법과 이유
- 전달 1건·이번 달 1건만 두기: 잘못된 구현도 1을 반환한다.
- JVM 시간대만 UTC로 실행: 실행 시각이 월 경계가 아니면 월 계산 오류를 검출하지 못한다.

## 선택한 방법
두 달의 결근 수를 2 대 1로 다르게 만들고 한국 1일 00:30에서 검증한다. 날짜는 기존 고정 Clock의 월에서 계산한다.

## 전후 수치·결과
일시적으로 AttendanceService의 월을 Clock instant의 UTC 월로, AttendanceStore의 homeSnapshot 월도 해당 한국 자정의 UTC 월로 변경했다. 새 테스트 **1개 실패**, 두 assertion 모두 `expected: 1 but was: 2`. 시험 종료 trap으로 두 운영 파일을 HEAD 내용으로 즉시 원복했고 git diff가 없음을 확인했다.

원복 후 M5HomeCountersTest **4/4 성공**, 실패·오류·건너뜀 0. 운영 Java 변경은 이 작업의 커밋에 포함하지 않는다. 전체 UTC 결과는 최종 리뷰 보고서에 기록한다.

## 부작용·남은 위험
검증을 위해 당일 결근 행을 직접 만든다. 실제 결근 배치가 미래/당일을 실행할 수 있다는 의미가 아니라 조회 API의 월 범위를 검사하는 fixture다.
