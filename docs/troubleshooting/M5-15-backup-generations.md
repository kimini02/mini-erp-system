# M5-15 중지 기간과 관계없이 최근 백업 7세트 보관

## 증상
7일 넘게 중지했다가 켠 뒤 자동 백업이 실행되면 기존 세대가 모두 오래됐다는 이유로 지워져 한 세대만 남는다.

## 재현 방법
Ubuntu 24.04의 임시 폴더에 UTC 이름 순 백업 9세트를 만들고 각 세트에 dump·sha256·version·counts.tsv를 두었다. 앞 8세트는 20일 전 mtime, 마지막 한 세트는 현재 mtime. 기존 find -mmin +10080은 1세트만 남겼다.

## 원인
실험할 때만 켜는 운영에서 일수는 남길 복구 세대 수를 보장하지 않는다.

## 검토했지만 버린 방법과 이유
- 보관 일수를 늘리기: 그보다 오래 중지하면 같은 문제가 생긴다.
- dump만 정리: 짝 파일이 계속 남거나 복구에 필요한 메타데이터와 맞지 않는다.

## 선택한 방법
성공한 backup_now의 마지막에 공통 prune_backups를 호출한다. UTC 파일 이름 역순으로 7개 dump를 남기고 초과 dump와 알려진 세 suffix를 함께 제거한다. 수동·타이머·배포 전 백업이 같은 규칙을 쓴다. 기존 maintenance/backup 잠금 안에서 정리한다. 시스템 폴더 권한을 변경하지 않는다.

## 전후 수치·결과
기존 9세트 → 1세트. 새 정리 9세트/36파일 → 7세트/28파일. 다시 실행하면 추가 제거 0세트. 아래는 새 정리 출력이다.

```text
BACKUP_RETAIN sets=7 removed_sets=2
RETENTION_AFTER sets=7 files=28 removed_sets=2 sidecars=MATCH
20261003T000000.000000000Z.sql.gz
20261004T000000.000000000Z.sql.gz
20261005T000000.000000000Z.sql.gz
20261006T000000.000000000Z.sql.gz
20261007T000000.000000000Z.sql.gz
20261008T000000.000000000Z.sql.gz
20261009T000000.000000000Z.sql.gz
BACKUP_RETAIN sets=7 removed_sets=0
```

첫 구현 검사에서 find 출력 줄바꿈의 이중 이스케이프를 검출해 수정한 뒤 세트·짝 파일 수를 다시 단언했다. 이 실패는 커밋 전 시험에서 확인했으며 운영 데이터에는 적용하지 않았다.

## 부작용·남은 위험
이번 사용자 지시가 명세의 기존 일수 보관보다 우선한다. 자주 배포하면 배포 전 백업도 세대 수를 쓰므로 오래된 날짜가 빨리 밀릴 수 있다. 저장 공간은 세트 수로 제한되지만 각 dump 크기는 증가할 수 있다. 서버 장애에 대비한 외부 보관은 여전히 운영자가 수행한다.
